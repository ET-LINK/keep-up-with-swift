# Swift Club · Evolution Line Map

**English** · [简体中文](README.zh-CN.md)

**Live site: <https://et-link.github.io/swift-club/>** · [中文版 (Chinese)](https://et-link.github.io/swift-club/?lang=zh)

An interactive learning site for the new features of Swift 6.0 → 6.4 (Sep 2024 – Sep 2026), drawn as a metro line map:

- **6 themed lines** × **5 release “fare zones”**, 80 feature stations in all
- **Before you board (5.x)**: 8 basics stations on `async`/`await`, tasks, actors, `@MainActor`, `Sendable`, and continuations (Swift 5.5 – 5.10), taught in Swift 6 language mode. They sit before 6.0 on the Concurrency line and aren't counted as new features
- Every station: a one-sentence explanation, old-versus-new code, **the compiler's real output**, and for some a quick quiz
- **3 labs**: a concurrency execution trace (nonisolated vs nonsending vs @concurrent), an ownership sandbox (~Copyable), and a memory-layout viewer (Array / InlineArray / Span)
- **Guess the Compiler**: 17 snippets, with the answers given by the compiler itself
- **Proposal index**: all 156 Swift Evolution proposals since 6.0, filterable by release and line, with a preview of 6.5
- **Pass**: punch-card progress (stored only in your browser)
- **English by default, Chinese optional**: switch with the EN / 中文 control in the top bar

## Open it

Just open `index.html` in a browser; no server needed. Fonts load from Google Fonts and fall back to system fonts when offline.

`dist/swift-club.html` is a single-file build with the CSS, JS, and the data of every language inlined, meant for publishing. It leaves out the `<html>` / `<head>` shell (the publishing platform adds that), so open `index.html` when working locally.

## Languages

English is the default language and Chinese is optional.

- The language is chosen in this order: `?lang=` in the URL (for example `?lang=zh`), then the choice saved in this browser, then English.
- The switch in the top bar changes the language in place and updates the URL, so a copied link opens in the same language.
- Each language is a folder under `content/`, holding its lessons, labs, challenges, and interface strings. [`content/languages.json`](content/languages.json) lists them and names the default.
- The build produces one data bundle per language (`assets/data.<lang>.js`). The default language is loaded up front; the others are fetched when selected.
- The build also checks that the languages stay in step: the same features, code blocks, quiz structure, compiler verdicts, and interface keys. It rejects Chinese text in a language that isn't flagged `"cjk": true`, which catches a missed translation.

To add a language, copy `content/en/` to `content/<code>/`, translate its Markdown files, `site.json`, and `ui.json` (including the comments and strings inside code samples; the build recompiles them), then register it in `content/languages.json`.

## Real compilation

Not a single Swift snippet on the site is a hand-written “illustrative output”. The build script hands each one to the local `swiftc` to compile or run, then embeds the diagnostics and output verbatim. Code that is expected to fail must really fail and code that is expected to pass must really pass, or the build fails.

The current data was generated by `Apple Swift version 6.4.2`.

## Layout

```
content/
  languages.json           the languages, and which one is the default
  en/  zh/                 one folder per language
    5.x.md                   the “before you board” basics zone (flagged `"prelude": true` in site.json)
    6.0.md … 6.4.md          each release's features (a Markdown-style custom format)
    challenges.md            Guess the Compiler
    labs.md                  code and steps used by the labs
    site.json                lines, releases, express routes
    ui.json                  interface strings
src/page.html              page shell
assets/
  style.css                styles
  app.js                   page logic (routing, Swift highlighting, line map, labs, i18n… no dependencies)
  data.en.js  data.zh.js   generated data, one bundle per language
tools/
  build.mjs                build script
  evolution-snapshot.json  snapshot of the Swift Evolution proposal index (6.0+), plus the few earlier proposals the lessons cite
dist/swift-club.html       single-file build for publishing, every language inlined
```

## Rebuilding after a content change

```bash
node tools/build.mjs            # compile and verify every example (cached; only changed ones are recompiled)
node tools/build.mjs --fresh    # ignore the cache and recompile everything
node tools/build.mjs --no-compile   # don't call swiftc, use the cache only
```

You need Node 18+ and a Swift toolchain. Examples with the `testing` attribute need Xcode on macOS (to link Swift Testing / XCTest).

The compile cache `tools/.compile-cache.json` is committed too. If you only changed prose and left the code blocks alone, a machine without Swift can regenerate the site with `--no-compile`.

A code block looks like this:

````markdown
```swift title="This is an error in Swift 6 mode" check=error flags="-swift-version 6"
...
```
````

| Attribute | Meaning |
| --- | --- |
| `check=ok` / `error` / `warning` / `run` / `none` | must compile / must fail / must warn / compile and run / not compiled |
| `flags="…"` | swiftc flags, `-swift-version 6` by default |
| `script` | compile as top-level code in `main.swift` (implied by `run`) |
| `testing` | link Swift Testing and XCTest |
| `expect="…"` | text that must appear in the diagnostics or output |
| `hl="2,5-7"` | highlighted lines |

## Publishing (GitHub Pages)

Pages is set to publish from the root of the `main` branch. The `.nojekyll` file at the root makes Pages skip Jekyll and publish the files as they are; otherwise the `.md` files under `content/` that carry `---` metadata would be treated as pages.

To update the live site, rebuild locally, then commit and push the generated `assets/data.*.js`, `index.html`, and `dist/swift-club.html` together with your changes. It goes live a minute or two later. GitHub Pages lets browsers keep each file for 10 minutes, so `index.html` asks for every file with a fingerprint of its content (`assets/app.js?v=…`): once the new version is live, a normal refresh shows it.

There is no GitHub Actions build in the cloud because the build calls `swiftc`: a different Swift version can change the compiler output shown on the page.
