## default-isolation
title: Default isolation to the main actor
line: 1
se: 0466
level: core
short: Default MainActor
tags: default isolation MainActor main thread single-threaded app script -default-isolation defaultIsolation Approachable Concurrency
tldr: A compiler setting that infers `@MainActor` by default for everything in the module that doesn't state its isolation. For apps and scripts, most code is naturally single-threaded, so you no longer need to sprinkle `@MainActor` everywhere.

One pain point of Swift 6 mode is that UI-related types mostly need `@MainActor`, and forgetting one makes errors spread along the call chain. The `ProfilePresenter` below simply forgot its annotation:

```swift title="No annotation: the compiler doesn't know where the Presenter runs" check=error
@MainActor
final class ProfileView {
    func show(_ text: String) { print("Showing:", text) }
}

final class ProfilePresenter {
    let view = ProfileView()
    func present(name: String) {
        view.show("Hello, \(name)")
    }
}
```

```swift title="With -default-isolation MainActor, the same code passes as is" check=ok flags="-swift-version 6 -default-isolation MainActor"
@MainActor
final class ProfileView {
    func show(_ text: String) { print("Showing:", text) }
}

final class ProfilePresenter {
    let view = ProfileView()
    func present(name: String) {
        view.show("Hello, \(name)")
    }
}
```

```swift file=Package.swift check=none
.executableTarget(
    name: "MyApp",
    swiftSettings: [
        .defaultIsolation(MainActor.self),
        .enableUpcomingFeature("NonisolatedNonsendingByDefault"),
        .enableUpcomingFeature("InferIsolatedConformances"),
    ]
)
```

- It only affects declarations that **don't state an isolation explicitly**; code that explicitly says `nonisolated`, `@concurrent`, or another actor is untouched.
- It suits targets centered on the main flow: apps, command-line tools, and scripts. Libraries that many people reuse usually keep the default `nonisolated`.
- New app projects in Xcode 26 turn on **Default Actor Isolation = MainActor** and **Approachable Concurrency** by default; the latter includes this release's `NonisolatedNonsendingByDefault` and `InferIsolatedConformances`.
- When you need background work, mark it explicitly with [`@concurrent`](#f-concurrent).

::: quiz
? With `-default-isolation MainActor` on, what happens to a function that explicitly says `nonisolated`?
- It is changed to `@MainActor` too
+ It stays `nonisolated`; the default only applies to declarations that don't state an isolation
- A compile error: the two conflict
> Default isolation is just a “default when you write nothing”. Explicitly written isolation (`nonisolated`, `@concurrent`, `@SomeActor`) always wins.
:::

## nonsending
title: "`nonisolated(nonsending)`: async functions stay with their caller by default"
line: 1
se: 0461
flag: NonisolatedNonsendingByDefault
level: core
short: nonsending
tags: nonisolated nonsending async caller actor executor global concurrent thread pool hop
tldr: Until now a `nonisolated` `async` function always jumped to the global concurrent pool, “crossing threads” the moment you called it, which is why `Sendable` errors were everywhere. Now it runs on **the caller's actor** by default, matching the intuition you have for synchronous functions.

Since Swift 5.7 there has been a confusing rule: an `async` function that belongs to no actor leaves its caller when called and runs on the global concurrent executor (the thread pool). So the perfectly ordinary code below is an error in Swift 6 mode. `Model` is not `Sendable`, and calling `load()` “carries” it to another thread:

```swift title="Old rule: a nonisolated async function leaves the main actor" check=error
final class Model {
    var items: [String] = []
    func load() async { items.append("new data") }
}

@MainActor
final class ViewModel {
    let model = Model()
    func refresh() async {
        await model.load()
    }
}
```

Look at the wording in the compiler diagnostic: it already calls the old behavior `@concurrent`. With the upcoming feature on, the same code compiles, because `load()` now runs on the main actor and nothing crosses a thread:

```swift title="With NonisolatedNonsendingByDefault on" check=ok flags="-swift-version 6 -enable-upcoming-feature NonisolatedNonsendingByDefault"
final class Model {
    var items: [String] = []
    func load() async { items.append("new data") }
}

@MainActor
final class ViewModel {
    let model = Model()
    func refresh() async {
        await model.load()
    }
}
```

If you don't want to turn it on for everything, you can spell out the new behavior function by function:

```swift title="Without the upcoming feature, write nonisolated(nonsending) per function" check=ok
final class Model {
    var items: [String] = []
    nonisolated(nonsending) func load() async { items.append("new data") }
}

@MainActor
final class ViewModel {
    let model = Model()
    func refresh() async {
        await model.load()
    }
}
```

- Synchronous functions have always “run on the caller's thread”. Now async functions do too, and the mental model of the two is finally unified.
- When an `await` suspends, the main thread is still free and isn't “stuck”; it's only the **synchronous part** of the function that runs on the caller's actor.
- Migration: `swift package migrate --to-feature NonisolatedNonsendingByDefault` automatically adds `@concurrent` to functions that need to keep the old behavior.
- See the difference between the two rules animated: the [Concurrency Trace lab](#lab-concurrency).

::: quiz
? With `NonisolatedNonsendingByDefault` on, you `await` an ordinary `nonisolated async` function from a `@MainActor` method. Where does its synchronous code run?
- The global concurrent pool
+ The main actor, that is, the caller's isolation domain
- A newly created thread
> nonsending means “don't hand the call to another isolation domain”: the function inherits the caller's isolation. If you want the background, write `@concurrent` explicitly.
:::

## concurrent
title: "`@concurrent`: say so explicitly when you want parallelism"
line: 1
se: 0461
level: core
short: "@concurrent"
tags: concurrent parallel background thread pool expensive decode main thread
tldr: Want expensive work on the background thread pool? Add `@concurrent` to an `async` function. It always runs on the global concurrent executor and keeps the main actor free.

The new rule in one sentence: **stay put by default (nonsending), ask for parallelism explicitly (@concurrent)**.

```swift title="Hand heavy work like decoding to the background" check=ok flags="-swift-version 6 -enable-upcoming-feature NonisolatedNonsendingByDefault"
struct Photo: Sendable {
    let pixels: [UInt8]
}

enum PhotoDecoder {
    @concurrent
    static func decode(_ data: [UInt8]) async -> Photo {
        // imagine an expensive decode here
        Photo(pixels: data.map { 255 - $0 })
    }
}

@MainActor
final class PhotoViewModel {
    var photo: Photo?

    func load(_ data: [UInt8]) async {
        photo = await PhotoDecoder.decode(data)    // decoding happens in the background; the main thread isn't blocked
    }
}
```

Since a `@concurrent` function really does switch to another thread, the arguments you pass must be able to cross the isolation boundary safely:

```swift title="@concurrent crosses an isolation boundary, so arguments must be safe to pass" check=error flags="-swift-version 6 -enable-upcoming-feature NonisolatedNonsendingByDefault"
final class Draft {               // not Sendable
    var text = ""
}

@concurrent
func save(_ draft: Draft) async {
    print(draft.text)
}

@MainActor
final class Editor {
    let draft = Draft()
    func autosave() async {
        await save(draft)
    }
}
```

- `@concurrent` can only be used on `async` functions, and implies `nonisolated`.
- Don't mark every function `@concurrent`: switching threads has a cost of its own and brings `Sendable` requirements. Add it only to genuinely expensive computation.

## isolated-conformances
title: "Isolated conformances: main-actor types can conform to ordinary protocols"
line: 1
se: 0470
flag: InferIsolatedConformances
level: key
short: Isolated conformances
tags: isolated conformance protocol Equatable MainActor protocol conform global actor
tldr: Writing `@MainActor Equatable` means “this conformance is only valid on the main actor”. `@MainActor` types can finally implement ordinary protocols such as `Equatable` and `Hashable`, and the compiler guarantees it won't be called from another thread.

```swift title="Before: a main-actor type implementing Equatable is an error" check=error
@MainActor
final class Contact: Equatable {
    var name = ""

    static func == (a: Contact, b: Contact) -> Bool {
        a.name == b.name
    }
}
```

```swift title="Swift 6.2: @MainActor Equatable" check=ok hl="2"
@MainActor
final class Contact: @MainActor Equatable {
    var name = ""

    static func == (a: Contact, b: Contact) -> Bool {
        a.name == b.name
    }
}
```

With `InferIsolatedConformances` on, protocol conformances of main-actor types are inferred to be isolated automatically, so you don't even need to write `@MainActor`. The compiler guarantees safety: if you try to use the conformance outside the main actor, you get an error right away.

```swift title="The compiler guarantees an isolated conformance isn't carried to the background" check=error
protocol Describable {
    func describe() -> String
}

@MainActor
final class Label: @MainActor Describable {
    var text = "Hello"
    func describe() -> String { text }
}

@concurrent
func log<T: Describable>(_ value: T) async {
    print(value.describe())
}

@MainActor
func run() async {
    await log(Label())
}
```

## task-immediate
title: "`Task.immediate`: start running right now, in the current context"
line: 1
se: 0472
level: key
short: Task.immediate
tags: Task immediate synchronous start scheduling order UI event
tldr: An ordinary `Task { }` just puts the task in a queue to run later. `Task.immediate { }` runs **immediately** and synchronously on the current thread, up to the first real suspension point.

```swift title="Comparing the execution order" check=run
@MainActor
func demo() async {
    print("1. start")
    Task {
        print("4. ordinary Task: runs only after the current code yields the main thread")
    }
    Task.immediate {
        print("2. Task.immediate: runs right now, synchronously")
    }
    print("3. back in the caller")
    try? await Task.sleep(for: .milliseconds(50))
}

await demo()
```

It suits UI event handling: after a button tap you want to update UI state immediately (say, show a loading indicator) and then go do async work. With an ordinary `Task`, the UI may render one frame of the old state first.

## isolated-deinit
title: "`isolated deinit`: run deinitializers on the actor"
line: 1
se: 0371
level: brief
short: isolated deinit
tags: deinit deinitializer isolated MainActor cleanup
tldr: The `deinit` of a `@MainActor` class is nonisolated by default and can't call main-actor methods. Write `isolated deinit` and the deinitializer runs on the main actor.

```swift title="An ordinary deinit can't call main-actor methods" check=error
@MainActor
final class SessionController {
    func stopTimers() { print("Stopping timers") }

    deinit {
        stopTimers()
    }
}
```

```swift title="isolated deinit" check=ok
@MainActor
final class SessionController {
    func stopTimers() { print("Stopping timers") }

    isolated deinit {
        stopTimers()
    }
}
```

If the last release of the object happens on another thread, the runtime schedules the deinitializer onto the main actor, so deinitialization may run slightly later.

## inlinearray
title: "`InlineArray` and `[N of T]`: fixed-length arrays that stay off the heap"
line: 2
se: 0453, 0483
level: core
short: InlineArray
tags: InlineArray fixed-size array stack heap allocation performance [N of T]
tldr: "`InlineArray<4, Int>` (shorthand `[4 of Int]`) is an array whose length is written into its type: the elements live inline, on the stack or inside the owning struct, with no heap allocation, no reference counting, and no copy-on-write."

`Array` itself is just a pointer; the real elements live on the heap, with reference counting and copy-on-write attached. For data whose length is always 4, that overhead is wasteful:

```swift title="Comparing the memory layout with Array" check=run
let dynamic: [Int] = [1, 2, 3, 4]
let fixed: [4 of Int] = [1, 2, 3, 4]          // shorthand for InlineArray<4, Int>

print(MemoryLayout.size(ofValue: dynamic))     // just a pointer to the heap
print(MemoryLayout.size(ofValue: fixed))       // four Ints stored in place
```

```swift title="Basic usage" check=run
var rgb: [3 of UInt8] = [255, 128, 0]
rgb[1] = 200                                   // elements can be modified
print(rgb.count, rgb[1])

let board = [9 of Character](repeating: "·")  // initialize with a repeated value
print(board.count)

for i in rgb.indices {                         // in 6.2 it isn't a Sequence; iterate with indices
    print(i, rgb[i])
}
```

The length is part of the type, so you can't `append` or `remove`, and a literal must have exactly the right number of elements:

```swift title="The number of elements must match the type" check=error
let rgb: [3 of UInt8] = [255, 128]
```

- Good for: small fixed buffers, coordinates/colors/matrices, embedded development, and performance hot spots.
- Not for: collections whose length changes, or large N (it takes a lot of stack space and is expensive to copy).
- When the elements are copyable, `InlineArray` is copyable too, and copying **really copies every element**, unlike `Array`'s copy-on-write.
- After Swift 6.4 introduced [`Iterable`](#f-iterable), `InlineArray` can be iterated with `for-in` directly.
- See the layout of different element types: the [Memory Layout lab](#lab-memory).

::: quiz
? What is `MemoryLayout<[5 of Int]>.size` on a 64-bit platform?
- 8, just a pointer like `Array`
+ 40, all five `Int`s stored inline
- 48, because it also needs a length field
> The length is in the type and needn't be stored at runtime, so an `InlineArray`'s size is just N × the element's stride: 5 × 8 = 40.
:::

## integer-generics
title: "Integer generic parameters: `<let N: Int>`"
line: 2
se: 0452
level: key
short: Integer generics
tags: integer generic let N value generics matrix compile-time
tldr: "Generic parameters can be integers as well as types: `struct Matrix<let rows: Int, let columns: Int>`. This is how `InlineArray`'s length parameter is implemented."

```swift check=run
struct Matrix<let rows: Int, let columns: Int> {
    var storage: [rows of [columns of Double]]

    init(repeating value: Double) {
        storage = .init(repeating: .init(repeating: value))
    }

    var shape: String { "\(rows)×\(columns)" }    // in code it can be read like a value
}

let m = Matrix<2, 3>(repeating: 0)
print(m.shape)
print(MemoryLayout<Matrix<2, 3>>.size)    // 6 Doubles, all stored inline
```

`Matrix<2, 3>` and `Matrix<3, 2>` are two different types, so “shape mismatch” errors can be caught at compile time. For now an integer generic argument can only be an `Int` literal or another integer generic parameter; computations such as `N + 1` aren't supported yet.

## span
title: "`Span`: safe, zero-overhead access to contiguous memory"
line: 2
se: 0447, 0456, 0467, 0485, 0464
level: core
short: Span
tags: Span MutableSpan RawSpan OutputSpan UTF8Span contiguous memory pointer memory safety lifetime
tldr: "`Span<T>` is a read-only view over a run of contiguous memory (`MutableSpan` is writable). It is as fast as `UnsafeBufferPointer`, but the compiler guarantees it can't outlive the original data: dangling pointers and use-after-free are ruled out at compile time."

To process “a run of contiguous elements” efficiently you used to either accept an `Array` (which may trigger a copy) or grab a pointer with `withUnsafeBufferPointer` (unsafe). `Span` is the third way:

```swift title="A function that takes a Span: both Array and InlineArray can be passed" check=run
func checksum(_ bytes: Span<UInt8>) -> UInt8 {
    var sum: UInt8 = 0
    for i in bytes.indices {
        sum &+= bytes[i]
    }
    return sum
}

let packet: [UInt8] = [0x12, 0x34, 0x56]
let header: [4 of UInt8] = [1, 2, 3, 4]

print(checksum(packet.span))
print(checksum(header.span))
```

```swift title="MutableSpan: modify in place" check=run
func amplify(_ samples: inout [Float]) {
    var view = samples.mutableSpan       // borrows samples exclusively
    for i in view.indices {
        view[i] *= 2
    }
}

var samples: [Float] = [0.5, -1.2, 3.3]
amplify(&samples)
print(samples)
```

Note that the `mutableSpan` above is used inside a function: variables declared at the top level of `main.swift` are actually globals, and globals can't hold nonescapable values like `Span`.

`Span` is `~Escapable`: its lifetime depends on the data that provides it. Trying to make it live longer than the source data is a compile error, not a runtime crash:

```swift title="A Span can't escape the scope of its source data" check=error
func leak() -> Int {
    var escaped: Span<UInt8>
    do {
        let data: [UInt8] = [1, 2, 3]
        escaped = data.span
    }
    return escaped.count
}
```

- `Array`, `ContiguousArray`, `ArraySlice`, `InlineArray`, `String.UTF8View`, and others all provide a `.span` property (SE-0456).
- A `Span` can't be stored in a global variable, a class property, or an escaping closure; it fits as a function parameter, saying “I only need to look at these elements temporarily”.
- Out-of-bounds accesses are still checked at runtime, so safety isn't reduced, but there is no reference counting or exclusivity-checking overhead.
- The same family: `RawSpan` (raw bytes), `MutableSpan`, `OutputSpan` (initializing uninitialized memory), and `UTF8Span` (safe handling of UTF-8).
- Follow-ups: 6.4's [`withTemporaryAllocation`](#f-temp-alloc), [safe `RawSpan` loading](#f-rawspan-load), and two-way bridging with C++ `std::span`.

## nonescapable
title: "`~Escapable`: types that can't escape"
line: 2
se: 0446, 0465
level: brief
short: ~Escapable
tags: Escapable nonescapable escape lifetime dependency
tldr: "The language capability behind `Span`. Ordinary types are `Escapable` by default, so their values can be stored and passed around freely; a value of a `~Escapable` type can only be used while the thing it depends on is still alive."

`~Escapable` and `~Copyable` are siblings: one removes the default ability to be copied, the other removes the default ability to escape. The standard library filled in the infrastructure for them in 6.2 (SE-0465); for example, `Optional` can wrap a nonescapable value.

When you define a `~Escapable` type yourself you need a lifetime dependency to say “who does this value depend on”. As of 6.4 that annotation is still experimental (`@_lifetime`), and the compiler flatly rejects code that doesn't state the dependency:

```swift title="Without a lifetime annotation, the compiler can't confirm safety" check=error
struct Window: ~Escapable {
    let items: Span<Int>
}
```

In everyday development you will most likely just **use** ready-made nonescapable types like `Span`, rather than define your own.

## memory-safety
title: Strict memory-safety checking
line: 2
se: 0458
level: key
short: Memory safety
tags: strict memory safety unsafe pointer audit -strict-memory-safety
tldr: With `-strict-memory-safety` on, every place that uses an unsafe construct (pointers, `unsafe` APIs) gets flagged. You can switch to a safe alternative, or use an `unsafe` expression to say clearly “this is intentional”.

```swift title="With it on, unsafe usages are flagged one by one" check=warning flags="-swift-version 6 -strict-memory-safety"
func sum(_ p: UnsafePointer<Int>, count: Int) -> Int {
    var total = 0
    for i in 0..<count {
        total += p[i]
    }
    return total
}
```

```swift title="Option 1: mark it with unsafe, which makes code audits easier" check=ok flags="-swift-version 6 -strict-memory-safety"
func sum(_ p: UnsafePointer<Int>, count: Int) -> Int {
    var total = 0
    for i in 0..<count {
        total += unsafe p[i]
    }
    return total
}
```

```swift title="Option 2 (better): switch to Span and the warning goes away on its own" check=ok flags="-swift-version 6 -strict-memory-safety"
func sum(_ values: Span<Int>) -> Int {
    var total = 0
    for i in values.indices {
        total += values[i]
    }
    return total
}
```

This is an opt-in mode, and the official position is that most projects don't need it. It suits code with the highest safety requirements: components that parse untrusted input, cryptography libraries, and system services. Like `try` and `await`, `unsafe` is only a marker and doesn't change runtime behavior.

## observations
title: "`Observations`: observe @Observable with an async sequence"
line: 4
se: 0475
level: key
short: Observations
tags: Observation Observable Observations async sequence observe transaction SwiftUI
tldr: "`Observations { … }` turns changes to an `@Observable` object into an async sequence. Several modifications inside one transaction produce just one update, and what you receive is always a consistent snapshot."

```swift title="Modify two properties at once and receive just one update" check=run
import Observation

@Observable
final class Cart {
    var count = 0
    var total = 0.0
}

@MainActor
func watch() async {
    let cart = Cart()
    let summaries = Observations { "Items: \(cart.count), total: $\(cart.total)" }

    Task {
        for price in [12.5, 30.0] {
            cart.count += 1            // two modifications in the same transaction…
            cart.total += price        // …produce only one update
            try? await Task.sleep(for: .milliseconds(20))
        }
    }

    var received = 0
    for await summary in summaries {
        print(summary)
        received += 1
        if received == 3 { break }
    }
}

await watch()
```

Outside SwiftUI, observing an [`@Observable`](#f-observable) used to require `withObservationTracking`, which notifies only once and has to be re-registered by hand. `Observations` solves that. 6.4 adds finer-grained control; see [advanced observation tracking](#f-observation-tracking).

## nonexhaustive
title: "`@nonexhaustive`: declare “more cases may be added later”"
since: 6.2.3
line: 3
se: 0487
level: brief
short: "@nonexhaustive"
tags: enum nonexhaustive exhaustive unknown default package API evolution
tldr: In an ordinary Swift package, adding a case to a public enum breaks the `switch` of every client. Mark it `@nonexhaustive` and other modules must write `@unknown default`, so adding cases later is no longer a breaking change.

```swift check=ok
@nonexhaustive
public enum PaymentMethod {
    case card
    case cash
}

// Within the same module (or the same package) you can still switch exhaustively, with no @unknown default
func label(for method: PaymentMethod) -> String {
    switch method {
    case .card: "Card"
    case .cash: "Cash"
    }
}
```

Previously only binary frameworks with library evolution turned on had this kind of “non-frozen enum”. This feature arrived in Swift 6.2.3.
