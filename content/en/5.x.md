## async-await
title: "`async` / `await`: functions that can pause"
line: 1
se: 0296
since: 5.5
level: core
short: async/await
tags: async await asynchronous suspend suspension point pause try await throws completion handler callback top-level
tldr: An `async` function can **pause** while it waits for something slow (the network, a timer, another task) without blocking its thread. Every place where it might pause is marked with `await`, so the pauses are visible in the code.

Before Swift 5.5, waiting for something slow meant passing a completion handler: the result arrived later, inside a closure, and error handling was split across callbacks. An `async` function simply returns its result, and the caller writes `await` where it may have to wait:

```swift title="Call async functions with await" check=run
func fetchTemperature(city: String) async -> Int {
    try? await Task.sleep(for: .milliseconds(100))   // pretend this is a network request
    return city == "Oslo" ? 4 : 21
}

let oslo = await fetchTemperature(city: "Oslo")      // pauses here until the result is ready
let rome = await fetchTemperature(city: "Rome")
print("Oslo \(oslo)°C, Rome \(rome)°C")
```

While a function is paused at an `await`, its thread isn't blocked: the thread goes off to run other work, and the function continues once the result is ready. That is also why `await` is only allowed where pausing is possible. An ordinary synchronous function can't pause, so the compiler rejects it:

```swift title="A synchronous function can't await" check=error hl="4"
func fetchTemperature(city: String) async -> Int { 21 }

func report() {                                   // an ordinary synchronous function
    let rome = await fetchTemperature(city: "Rome")
    print(rome)
}
```

The fix is either to make `report()` `async` as well, or to start a `Task` from it: that's the [next station](#f-task).

Errors work the way you already know. A function can be both `async` and `throws`, and you call it with `try await`:

```swift title="async throws and try await" check=run
struct OfflineError: Error {}

func download(_ name: String) async throws -> String {
    if name.isEmpty { throw OfflineError() }
    try await Task.sleep(for: .milliseconds(50))
    return "contents of \(name)"
}

do {
    print(try await download("notes.txt"))
    print(try await download(""))
} catch {
    print("Failed:", error)
}
```

- `await` marks a **possible suspension point**. Between two `await`s your code runs without interruption; across an `await`, other code may run in the meantime. Keep that in mind for [actors](#f-actor).
- You can `await` inside an `async` function, inside a `Task { }`, and at the top level of `main.swift` or a Playground. That's why the examples on this site can call `await` directly.
- `for await item in sequence` waits for the elements of an async sequence one by one; you'll use it with [task groups](#f-structured).

::: quiz
? Where can you call `await fetchTemperature(city:)` directly?
- In any function, as long as you write `await`
+ In an `async` function, inside a `Task { }`, or at the top level of `main.swift`
- Only on the main thread
> `await` needs a context that is able to pause. A synchronous function isn't, so the compiler rejects the call there; start a `Task` instead.
:::

## task
title: "`Task`: start async work, and cancel it"
line: 1
se: 0304
since: 5.5
level: core
short: Task
tags: Task unstructured task detached value cancel cancellation cooperative isCancelled checkCancellation CancellationError
tldr: "`Task { }` starts async work from anywhere, even from synchronous code. It gives you a handle: `await task.value` waits for the result, and `task.cancel()` **asks** the task to stop. Cancellation is cooperative: the task has to check for it."

A `Task` is a unit of async work that runs alongside the code that created it. Creating one doesn't wait for it; the handle lets you collect the result later:

```swift title="Start a task, keep going, collect the result" check=run
func fetchScore() async -> Int {
    try? await Task.sleep(for: .milliseconds(100))
    return 42
}

let task = Task {                     // scheduled to run alongside the code below
    await fetchScore()
}
print("Task created; the caller keeps going")
let score = await task.value          // now wait for its result
print("Score:", score)
```

This is also how synchronous code, a button handler for example, gets into the async world: it can't `await`, but it can always create a `Task`.

### Cancellation

`cancel()` doesn't stop a task by force. It sets a flag, and the task's own code decides when to stop. Async APIs such as `Task.sleep` check the flag for you and throw `CancellationError`:

```swift title="Cancel a download halfway" check=run expect="Stopped: CancellationError()"
let download = Task {
    for chunk in 1...5 {
        print("Downloading chunk", chunk)
        try await Task.sleep(for: .milliseconds(200))   // notices cancellation and throws
    }
    return "finished"
}

try? await Task.sleep(for: .milliseconds(500))
download.cancel()                                     // a request, not a kill
do {
    print(try await download.value)
} catch {
    print("Stopped:", error)
}
```

- Code that works for a long stretch without such calls has to check by itself: `if Task.isCancelled { … }`, or `try Task.checkCancellation()`, which throws `CancellationError`.
- `Task { }` takes on the actor of the code that creates it: started from the main actor, it runs on the main actor. `Task.detached { }` belongs to no actor at all. You'll meet both in [6.0's first station](#f-swift6-mode).
- If you drop the handle, the task still runs to the end; you just can't wait for it or cancel it any more. (6.4 warns when that would also lose an error: see [discarded throwing tasks](#f-task-unused).)

::: quiz
? You call `task.cancel()` while the task is in a long loop that never checks `Task.isCancelled` and never calls an async API. What happens?
- The task is stopped immediately, wherever it is
+ The loop keeps running to the end: cancellation is only a flag that the task must check
- The program crashes with a `CancellationError`
> Cancellation in Swift is cooperative. `cancel()` only sets a flag; the task decides when to look at it. That's also why [6.4's cancellation shields](#f-cancel-shield) exist: they hide the flag from cleanup code.
:::

## structured
title: "`async let` and task groups: structured concurrency"
line: 1
se: 0304, 0317
since: 5.5
level: core
short: async let · groups
tags: structured concurrency async let child task parallel TaskGroup withTaskGroup withThrowingTaskGroup addTask for await
tldr: "`async let` starts a **child task** that runs in parallel with the code that follows, and a task group does the same for any number of children. Children can't outlive their parent: it waits for all of them, and cancelling it cancels them too."

Two `await`s in a row run one after the other. When they don't depend on each other, `async let` starts both at once:

```swift title="One after another, then in parallel" check=run expect="about 200 ms"
func fetch(_ name: String) async -> String {
    try? await Task.sleep(for: .milliseconds(200))   // each fetch takes 0.2 s
    return name
}

func elapsed(since start: ContinuousClock.Instant) -> String {
    let ms = (ContinuousClock.now - start) / .milliseconds(1)
    return "about \(Int((ms / 100).rounded()) * 100) ms"
}

var start = ContinuousClock.now
let a = await fetch("A")
let b = await fetch("B")
print("One after another:", a, b, elapsed(since: start))

start = ContinuousClock.now
async let c = fetch("C")            // starts right away, as a child task
async let d = fetch("D")            // starts right away too
let (x, y) = await (c, d)           // wait for both
print("In parallel:", x, y, elapsed(since: start))
```

When the number of children is only known at run time, use a task group. Each `addTask` starts one child, and `for await` collects the results in the order the children finish:

```swift title="One child task per number" check=run
func square(_ n: Int) async -> Int {
    try? await Task.sleep(for: .milliseconds(40 * (6 - n)))   // bigger numbers finish sooner
    return n * n
}

let total = await withTaskGroup(of: Int.self) { group in
    for n in 1...5 {
        group.addTask { await square(n) }        // one child task per number
    }
    var sum = 0
    for await value in group {                   // in the order the children finish
        print("Got", value)
        sum += value
    }
    return sum
}
print("Sum of squares:", total)
```

- **Structured** means a child's lifetime is nested inside its parent's scope, like a local variable. When `withTaskGroup` returns, every child has finished; an `async let` you never `await` is cancelled and awaited when its scope ends.
- Cancelling the parent cancels all of its children. In `withThrowingTaskGroup`, an error from a child that is thrown out of the group cancels the children still running.
- The `Task { }` from the [previous station](#f-task) is **unstructured**: it can outlive the code that created it, so you manage it yourself.
- [Swift 6.1](#f-taskgroup-infer) lets you leave out `of: Int.self`.

::: quiz
? A function writes `async let x = work()` but returns without ever writing `await x`. What happens to `work()`?
- It never started
- It keeps running in the background after the function returns
+ Its child task is cancelled, and the function waits for it to finish before returning
> Child tasks can't outlive their scope. An `async let` that was never awaited is cancelled and then implicitly awaited when the scope ends, so nothing leaks.
:::

## actor
title: "`actor`: a type that guards its own state"
line: 1
se: 0306, 0313
since: 5.5
level: core
short: actor
tags: actor isolation isolated nonisolated mutable state data race serial reentrancy await
tldr: An actor is like a class whose mutable state **only one task at a time** can touch. Code outside the actor has to `await` to get in, so two tasks can never change that state at the same moment.

If two tasks modify the same class instance at the same time, that's a data race: updates get lost, or worse. An actor makes callers take turns. Below, a thousand child tasks increment one counter, and not one increment is lost:

```swift title="1,000 concurrent increments, none lost" check=run
actor Counter {
    private(set) var value = 0

    func increment() {          // inside the actor: plain synchronous code
        value += 1
    }
}

let counter = Counter()
await withTaskGroup(of: Void.self) { group in
    for _ in 1...1000 {
        group.addTask { await counter.increment() }   // from outside: await to get in
    }
}
print("Final value:", await counter.value)
```

Inside the actor, its methods use its state directly. From outside, every access is a call into another **isolation domain** and needs `await`. Assigning to an actor's property from outside isn't allowed at all, not even with `await`:

```swift title="From outside, you can't assign to an actor's property" check=error hl="6"
actor Counter {
    var value = 0
}

func reset(_ counter: Counter) async {
    await counter.value = 0
}
```

As the note suggests, give the actor a method that makes the change. Members that don't touch mutable state can be marked `nonisolated`, and then they're used without `await`:

```swift title="nonisolated: no await needed" check=run
actor BankAccount {
    let number: String                 // a constant: nothing to protect
    private var balance = 0

    init(number: String) { self.number = number }

    func deposit(_ amount: Int) -> Int {
        balance += amount
        return balance
    }

    nonisolated var label: String {    // reads only the constant
        "Account #\(number)"
    }
}

let account = BankAccount(number: "42")
print(account.label)                   // no await
print("Balance:", await account.deposit(100))
```

- Actors are reference types like classes, but they can't be subclassed, and they're always [`Sendable`](#f-sendable): passing an actor around is safe because it protects itself.
- **Reentrancy**: while one of its methods is paused at an `await`, an actor may run other calls. Don't assume its state is unchanged across an `await` inside an actor method.
- An actor doesn't own a thread; it runs on the shared thread pool. Waiting to get into an actor suspends only your task, and no thread is blocked.

::: quiz
? An actor method reads `balance`, then `await`s a network call, then writes `balance` back. What should you watch out for?
- Nothing: the actor stays locked for the whole method call
+ Other calls may run on the actor during the `await`, so `balance` may have changed in the meantime
- The compiler requires the method to be `nonisolated`
> Actors are reentrant: while one call is paused at an `await`, the actor can run others. Re-read the state after each `await`, or finish the change before you await.
:::

## main-actor
title: "`@MainActor`: the actor of the main thread"
line: 1
se: 0316
since: 5.5
level: core
short: "@MainActor"
tags: MainActor global actor main thread UI UIKit SwiftUI AppKit isolation attribute
tldr: "`@MainActor` is a **global actor**: one actor shared by the whole program, and it runs on the main thread. Mark UI code with it, and the compiler makes sure that code only ever runs on the main thread."

UI frameworks may only be used from the main thread, so Swift models the main thread as an actor too: the main actor. Put `@MainActor` on a type, a function, or a property, and it's isolated to that actor. Calls from the same actor are direct; calls from anywhere else need `await`:

```swift title="Same actor: call directly. Another domain: await" check=run
@MainActor
final class ScoreBoard {
    var score = 0
    func add(_ points: Int) { score += points }
}

@MainActor
func tapButton(_ board: ScoreBoard) {
    board.add(1)                       // same actor: call it directly
}

func syncFromServer(_ board: ScoreBoard) async {   // belongs to no actor
    await board.add(10)                // a different actor: hop over with await
}

let board = ScoreBoard()
tapButton(board)                       // top-level code already runs on the main actor
await syncFromServer(board)
print("Score:", board.score)
```

Forget the `await`, and the compiler stops you:

```swift title="Calling into the main actor without await" check=error hl="8"
@MainActor
final class ScoreBoard {
    var score = 0
    func add(_ points: Int) { score += points }
}

func syncFromServer(_ board: ScoreBoard) async {
    board.add(10)
}
```

- A `@MainActor` class is `Sendable`: the main actor protects its state, so it can be shared freely.
- SwiftUI views and UIKit view controllers are already `@MainActor`, and so is top-level code in `main.swift`.
- `Task { }` started on the main actor runs on the main actor. That makes it the usual way to start async work from a button tap.
- [Swift 6.2](#f-default-isolation) can make `@MainActor` the default for a whole module, so you don't have to write it everywhere.

::: quiz
? A function that belongs to no actor calls a method on a `@MainActor` class. What does it need to write?
- Nothing: the method moves itself to the main thread
+ `await`, because the call crosses into the main actor
- `DispatchQueue.main.async { }` around the call
> A call into another isolation domain is asynchronous: the caller hops onto the main actor, waiting if the main actor is busy. In Swift 6 mode the compiler checks this for you.
:::

## sendable
title: "`Sendable`: what may cross between isolation domains"
line: 1
se: 0302
since: 5.5
level: core
short: Sendable
tags: Sendable @Sendable closure isolation domain boundary data race value type struct final class unchecked
tldr: Each actor, and the code that belongs to no actor, is its own **isolation domain**. A value may cross from one domain into another only if it's `Sendable`, meaning safe to use from both sides at once. Value types usually are; classes with mutable state aren't.

An actor protects its own state, but what about the values you pass in and out? Hand a mutable class instance to an actor and keep using it yourself, and two domains share one object: a data race again. In Swift 6 mode the compiler catches it:

```swift title="Sending a mutable object and still using it" check=error hl="12,13"
final class Draft {                     // a class with mutable state: not Sendable
    var text = ""
}

actor Outbox {
    func send(_ draft: Draft) { print("Sending:", draft.text) }
}

func compose(using outbox: Outbox) async {
    let draft = Draft()
    draft.text = "Hello"
    await outbox.send(draft)             // hand it to the actor's domain…
    draft.text = "Changed my mind"       // …while still changing it here
}
```

Make `Draft` a `struct` and the problem disappears: the actor gets its own copy, and each side changes only its own:

```swift title="A value type is copied: each domain gets its own" check=ok
struct Draft {                          // a value type: Sendable automatically
    var text = ""
}

actor Outbox {
    func send(_ draft: Draft) { print("Sending:", draft.text) }
}

func compose(using outbox: Outbox) async {
    var draft = Draft()
    draft.text = "Hello"
    await outbox.send(draft)             // the actor gets its own copy
    draft.text = "Changed my mind"       // changes only our copy
}
```

If `compose` never touched `draft` after sending it, even the class version would compile, because Swift 6 can prove that nobody else uses it any more. That's [6.0's region-based isolation](#f-region-sending).

Which types are `Sendable`?

| Type | Sendable? |
| --- | --- |
| `Int`, `String`, `Bool`, … | Yes |
| Arrays, dictionaries, and optionals of Sendable values | Yes |
| A `struct` or `enum` whose stored properties are all Sendable | Yes. Inferred inside the module; `public` types must declare it |
| An `actor`, or a `@MainActor` class | Yes: the actor protects the state |
| A `final class` whose stored properties are all Sendable `let`s | Yes, once it declares `: Sendable` |
| A class with a `var` stored property | No |

Closures cross domains too. A closure type marked `@Sendable` may run concurrently with other code, so it can't modify the local variables it captures:

```swift title="A @Sendable closure can't mutate what it captures" check=error hl="4"
func countClicks() {
    var clicks = 0
    let onClick: @Sendable () -> Void = {   // may run concurrently with other code
        clicks += 1
    }
    onClick()
}
```

- `@unchecked Sendable` tells the compiler “trust me, I synchronize this myself”, for example with a lock. The compiler then stops checking that type, so use it sparingly; 6.0's [`Mutex`](#f-synchronization) usually makes it unnecessary.
- The checks arrived gradually: 5.5 introduced the protocol, later 5.x releases added the checks as warnings (with `-strict-concurrency=complete`), and Swift 6 language mode makes them errors. That's [6.0's first station](#f-swift6-mode).

::: note Trying these in Xcode?
The examples here are compiled in Swift 6 language mode. In a target that is still set to Swift 5 mode, the errors on this page are only warnings, or don't appear at all. Check **Swift Language Version** in the build settings.
:::

::: quiz
? Which of these types is **not** `Sendable`?
- `struct Point { var x: Int; var y: Int }`
- `actor Store { var items: [String] = [] }`
+ `final class Box { var value = 0 }`
- `[String: Int]`
> Value types made of Sendable parts are Sendable, and actors protect themselves. A class with a mutable `var` can be changed from two domains at once, so it isn't Sendable unless it guards that state itself (by being an actor, by using a `Mutex`, …).
:::

## where-async-runs
title: Where does an async function run?
line: 1
se: 0338
since: 5.7
level: key
short: Where it runs
tags: executor global concurrent executor thread pool hop isolation nonisolated async main thread
tldr: An async function runs according to its **isolation**: an actor's method on that actor, a `@MainActor` function on the main thread, and a function that belongs to no actor on the **global concurrent pool**. A call that changes isolation is a “hop”.

Synchronous functions run on whatever thread calls them. Async functions are different: where they run is decided by their own isolation, not by the caller. Watch the main thread being left and re-entered:

```swift title="A nonisolated async function leaves the main actor" check=run expect="work() runs on a pool thread"
import Foundation

func whereAmI() -> String { Thread.isMainThread ? "the main thread" : "a pool thread" }

func work() async {                               // belongs to no actor
    print("  work() runs on", whereAmI())
}

@MainActor
func start() async {
    print("start() runs on", whereAmI())
    await work()                                  // hop: leave the main actor
    print("start() resumes on", whereAmI())      // hop back
}

await start()
```

This rule comes from SE-0338, in Swift 5.7. Before that, such a function kept running on whichever actor called it, which could tie up the main actor with work that was meant for the background. Since 5.7, a function that belongs to no actor always runs on the global concurrent pool, a set of threads shared by all tasks.

The rule is predictable, but it has a cost: everything you pass to `work()` crosses from the main actor into another domain, so it has to be [`Sendable`](#f-sendable). That's where many Swift 6 errors come from, and why Swift 6.2 lets you flip the default. Here's the same code with 6.2's upcoming feature turned on:

```swift title="The same code with NonisolatedNonsendingByDefault (Swift 6.2)" check=run flags="-swift-version 6 -enable-upcoming-feature NonisolatedNonsendingByDefault" expect="work() runs on the main thread"
import Foundation

func whereAmI() -> String { Thread.isMainThread ? "the main thread" : "a pool thread" }

func work() async {                               // belongs to no actor
    print("  work() runs on", whereAmI())
}

@MainActor
func start() async {
    print("start() runs on", whereAmI())
    await work()                                  // now stays with its caller
    print("start() resumes on", whereAmI())
}

await start()
```

- A hop is cheap but not free. More importantly, every hop is a boundary that values have to cross safely.
- Under the new default, mark a function [`@concurrent`](#f-concurrent) to keep the old behavior; without the upcoming feature, write [`nonisolated(nonsending)`](#f-nonsending) to get the new behavior one function at a time.
- Step through both rules in the [Concurrency Trace lab](#lab-concurrency).

::: note Trying this in Xcode?
New app projects in Xcode 26 turn on **Approachable Concurrency**, which includes `NonisolatedNonsendingByDefault`. In such a project the first example also prints “the main thread” for `work()`: you're seeing the 6.2 rule.
:::

::: quiz
? With no upcoming features on, a `@MainActor` function awaits an `async` function that belongs to no actor. Where does that function's code run?
- On the main thread, like its caller
+ On the global concurrent pool
- On a new thread created for that call
> Since SE-0338, a function that belongs to no actor runs on the global concurrent executor, a pool of threads shared by all tasks; no thread is created per call. 6.2's `nonisolated(nonsending)` lets it stay on the caller's actor instead.
:::

## checked-continuation
title: "Continuations: wrap a callback API in `async`"
line: 1
se: 0300
since: 5.5
level: brief
short: Continuations
tags: continuation withCheckedContinuation withCheckedThrowingContinuation CheckedContinuation resume callback completion handler bridge legacy
tldr: "`withCheckedContinuation` turns a completion-handler API into an `async` function: the task pauses until the callback calls `resume`, which must happen **exactly once**."

```swift title="From a completion handler to await" check=run
import Foundation

// An older API that reports its result through a completion handler
func legacyFetch(_ id: Int, completion: @escaping @Sendable (String) -> Void) {
    DispatchQueue.global().asyncAfter(deadline: .now() + 0.1) {
        completion("record #\(id)")
    }
}

func fetch(_ id: Int) async -> String {
    await withCheckedContinuation { continuation in
        legacyFetch(id) { value in
            continuation.resume(returning: value)   // resume exactly once
        }
    }
}

print(await fetch(7))
```

- For APIs that can fail, use `withCheckedThrowingContinuation` and `resume(throwing:)`.
- “Checked” means misuse is caught at run time: resuming twice crashes the program, and a continuation that is dropped without being resumed logs a warning, because the task waiting for it would otherwise hang forever.
- [6.4's `Continuation`](#f-continuation) turns “resumed twice” into a compile-time error.
