## async-await
title: "`async` / `await`: functions that can pause"
line: 1
se: 0296
since: 5.5
level: core
short: async/await
tags: async await asynchronous suspend suspension point pause try await throws completion handler callback top-level
tldr: An `async` function can **pause** while it waits for something slow (the network, a timer, another task) without blocking its thread. Every place where it might pause is marked with `await`, so the pauses are visible in the code.

Before Swift 5.5, waiting for something slow meant passing a completion handler: the result arrived later, inside a closure, and error handling was split across callbacks. An `async` function simply returns its result, and the caller writes `await` where it may have to wait:

```swift title="Call async functions with await" check=run
func fetchTemperature(city: String) async -> Int {
    try? await Task.sleep(for: .milliseconds(100))   // pretend this is a network request
    return city == "Oslo" ? 4 : 21
}

let oslo = await fetchTemperature(city: "Oslo")      // pauses here until the result is ready
let rome = await fetchTemperature(city: "Rome")
print("Oslo \(oslo)°C, Rome \(rome)°C")
```

While a function is paused at an `await`, its thread isn't blocked: the thread goes off to run other work, and the function continues once the result is ready. That is also why `await` is only allowed where pausing is possible. An ordinary synchronous function can't pause, so the compiler rejects it:

```swift title="A synchronous function can't await" check=error hl="4"
func fetchTemperature(city: String) async -> Int { 21 }

func report() {                                   // an ordinary synchronous function
    let rome = await fetchTemperature(city: "Rome")
    print(rome)
}
```

The fix is either to make `report()` `async` as well, or to start a `Task` from it: that's the [next station](#f-task).

Errors work the way you already know. A function can be both `async` and `throws`, and you call it with `try await`:

```swift title="async throws and try await" check=run
struct OfflineError: Error {}

func download(_ name: String) async throws -> String {
    if name.isEmpty { throw OfflineError() }
    try await Task.sleep(for: .milliseconds(50))
    return "contents of \(name)"
}

do {
    print(try await download("notes.txt"))
    print(try await download(""))
} catch {
    print("Failed:", error)
}
```

- `await` marks a **possible suspension point**. Between two `await`s your code runs without interruption; across an `await`, other code may run in the meantime. Keep that in mind for [actors](#f-actor).
- You can `await` inside an `async` function, inside a `Task { }`, and at the top level of `main.swift` or a Playground. That's why the examples on this site can call `await` directly.
- `for await item in sequence` waits for the elements of an async sequence one by one; you'll use it with [task groups](#f-structured).

::: quiz
? Where can you call `await fetchTemperature(city:)` directly?
- In any function, as long as you write `await`
+ In an `async` function, inside a `Task { }`, or at the top level of `main.swift`
- Only on the main thread
> `await` needs a context that is able to pause. A synchronous function isn't, so the compiler rejects the call there; start a `Task` instead.
:::

## task
title: "`Task`: start async work, and cancel it"
line: 1
se: 0304
since: 5.5
level: core
short: Task
tags: Task unstructured task detached value cancel cancellation cooperative isCancelled checkCancellation CancellationError
tldr: "`Task { }` starts async work from anywhere, even from synchronous code. It gives you a handle: `await task.value` waits for the result, and `task.cancel()` **asks** the task to stop. Cancellation is cooperative: the task has to check for it."

A `Task` is a unit of async work that runs alongside the code that created it. Creating one doesn't wait for it; the handle lets you collect the result later:

```swift title="Start a task, keep going, collect the result" check=run
func fetchScore() async -> Int {
    try? await Task.sleep(for: .milliseconds(100))
    return 42
}

let task = Task {                     // scheduled to run alongside the code below
    await fetchScore()
}
print("Task created; the caller keeps going")
let score = await task.value          // now wait for its result
print("Score:", score)
```

This is also how synchronous code, a button handler for example, gets into the async world: it can't `await`, but it can always create a `Task`.

### Cancellation

`cancel()` doesn't stop a task by force. It sets a flag, and the task's own code decides when to stop. Async APIs such as `Task.sleep` check the flag for you and throw `CancellationError`:

```swift title="Cancel a download halfway" check=run expect="Stopped: CancellationError()"
let download = Task {
    for chunk in 1...5 {
        print("Downloading chunk", chunk)
        try await Task.sleep(for: .milliseconds(200))   // notices cancellation and throws
    }
    return "finished"
}

try? await Task.sleep(for: .milliseconds(500))
download.cancel()                                     // a request, not a kill
do {
    print(try await download.value)
} catch {
    print("Stopped:", error)
}
```

- Code that works for a long stretch without such calls has to check by itself: `if Task.isCancelled { … }`, or `try Task.checkCancellation()`, which throws `CancellationError`.
- `Task { }` takes on the actor of the code that creates it: started from the main actor, it runs on the main actor. `Task.detached { }` belongs to no actor at all. You'll meet both in [6.0's first station](#f-swift6-mode).
- If you drop the handle, the task still runs to the end; you just can't wait for it or cancel it any more. (6.4 warns when that would also lose an error: see [discarded throwing tasks](#f-task-unused).)

::: quiz
? You call `task.cancel()` while the task is in a long loop that never checks `Task.isCancelled` and never calls an async API. What happens?
- The task is stopped immediately, wherever it is
+ The loop keeps running to the end: cancellation is only a flag that the task must check
- The program crashes with a `CancellationError`
> Cancellation in Swift is cooperative. `cancel()` only sets a flag; the task decides when to look at it. That's also why [6.4's cancellation shields](#f-cancel-shield) exist: they hide the flag from cleanup code.
:::

## structured
title: "`async let` and task groups: structured concurrency"
line: 1
se: 0304, 0317
since: 5.5
level: core
short: async let · groups
tags: structured concurrency async let child task parallel TaskGroup withTaskGroup withThrowingTaskGroup addTask for await
tldr: "`async let` starts a **child task** that runs in parallel with the code that follows, and a task group does the same for any number of children. Children can't outlive their parent: it waits for all of them, and cancelling it cancels them too."

Two `await`s in a row run one after the other. When they don't depend on each other, `async let` starts both at once:

```swift title="One after another, then in parallel" check=run expect="about 200 ms"
func fetch(_ name: String) async -> String {
    try? await Task.sleep(for: .milliseconds(200))   // each fetch takes 0.2 s
    return name
}

func elapsed(since start: ContinuousClock.Instant) -> String {
    let ms = (ContinuousClock.now - start) / .milliseconds(1)
    return "about \(Int((ms / 100).rounded()) * 100) ms"
}

var start = ContinuousClock.now
let a = await fetch("A")
let b = await fetch("B")
print("One after another:", a, b, elapsed(since: start))

start = ContinuousClock.now
async let c = fetch("C")            // starts right away, as a child task
async let d = fetch("D")            // starts right away too
let (x, y) = await (c, d)           // wait for both
print("In parallel:", x, y, elapsed(since: start))
```

When the number of children is only known at run time, use a task group. Each `addTask` starts one child, and `for await` collects the results in the order the children finish:

```swift title="One child task per number" check=run
func square(_ n: Int) async -> Int {
    try? await Task.sleep(for: .milliseconds(40 * (6 - n)))   // bigger numbers finish sooner
    return n * n
}

let total = await withTaskGroup(of: Int.self) { group in
    for n in 1...5 {
        group.addTask { await square(n) }        // one child task per number
    }
    var sum = 0
    for await value in group {                   // in the order the children finish
        print("Got", value)
        sum += value
    }
    return sum
}
print("Sum of squares:", total)
```

- **Structured** means a child's lifetime is nested inside its parent's scope, like a local variable. When `withTaskGroup` returns, every child has finished; an `async let` you never `await` is cancelled and awaited when its scope ends.
- Cancelling the parent cancels all of its children. In `withThrowingTaskGroup`, an error from a child that is thrown out of the group cancels the children still running.
- The `Task { }` from the [previous station](#f-task) is **unstructured**: it can outlive the code that created it, so you manage it yourself.
- [Swift 6.1](#f-taskgroup-infer) lets you leave out `of: Int.self`.

::: quiz
? A function writes `async let x = work()` but returns without ever writing `await x`. What happens to `work()`?
- It never started
- It keeps running in the background after the function returns
+ Its child task is cancelled, and the function waits for it to finish before returning
> Child tasks can't outlive their scope. An `async let` that was never awaited is cancelled and then implicitly awaited when the scope ends, so nothing leaks.
:::

## actor
title: "`actor`: a type that guards its own state"
line: 1
se: 0306, 0313
since: 5.5
level: core
short: actor
tags: actor isolation isolated nonisolated mutable state data race serial reentrancy await
tldr: An actor is like a class whose mutable state **only one task at a time** can touch. Code outside the actor has to `await` to get in, so two tasks can never change that state at the same moment.

If two tasks modify the same class instance at the same time, that's a data race: updates get lost, or worse. An actor makes callers take turns. Below, a thousand child tasks increment one counter, and not one increment is lost:

```swift title="1,000 concurrent increments, none lost" check=run
actor Counter {
    private(set) var value = 0

    func increment() {          // inside the actor: plain synchronous code
        value += 1
    }
}

let counter = Counter()
await withTaskGroup(of: Void.self) { group in
    for _ in 1...1000 {
        group.addTask { await counter.increment() }   // from outside: await to get in
    }
}
print("Final value:", await counter.value)
```

Inside the actor, its methods use its state directly. From outside, every access is a call into another **isolation domain** and needs `await`. Assigning to an actor's property from outside isn't allowed at all, not even with `await`:

```swift title="From outside, you can't assign to an actor's property" check=error hl="6"
actor Counter {
    var value = 0
}

func reset(_ counter: Counter) async {
    await counter.value = 0
}
```

As the note suggests, give the actor a method that makes the change. Members that don't touch mutable state can be marked `nonisolated`, and then they're used without `await`:

```swift title="nonisolated: no await needed" check=run
actor BankAccount {
    let number: String                 // a constant: nothing to protect
    private var balance = 0

    init(number: String) { self.number = number }

    func deposit(_ amount: Int) -> Int {
        balance += amount
        return balance
    }

    nonisolated var label: String {    // reads only the constant
        "Account #\(number)"
    }
}

let account = BankAccount(number: "42")
print(account.label)                   // no await
print("Balance:", await account.deposit(100))
```

- Actors are reference types like classes, but they can't be subclassed, and they're always [`Sendable`](#f-sendable): passing an actor around is safe because it protects itself.
- **Reentrancy**: while one of its methods is paused at an `await`, an actor may run other calls. Don't assume its state is unchanged across an `await` inside an actor method.
- An actor doesn't own a thread; it runs on the shared thread pool. Waiting to get into an actor suspends only your task, and no thread is blocked.

::: quiz
? An actor method reads `balance`, then `await`s a network call, then writes `balance` back. What should you watch out for?
- Nothing: the actor stays locked for the whole method call
+ Other calls may run on the actor during the `await`, so `balance` may have changed in the meantime
- The compiler requires the method to be `nonisolated`
> Actors are reentrant: while one call is paused at an `await`, the actor can run others. Re-read the state after each `await`, or finish the change before you await.
:::

## main-actor
title: "`@MainActor`: the actor of the main thread"
line: 1
se: 0316
since: 5.5
level: core
short: "@MainActor"
tags: MainActor global actor main thread UI UIKit SwiftUI AppKit isolation attribute
tldr: "`@MainActor` is a **global actor**: one actor shared by the whole program, and it runs on the main thread. Mark UI code with it, and the compiler makes sure that code only ever runs on the main thread."

UI frameworks may only be used from the main thread, so Swift models the main thread as an actor too: the main actor. Put `@MainActor` on a type, a function, or a property, and it's isolated to that actor. Calls from the same actor are direct; calls from anywhere else need `await`:

```swift title="Same actor: call directly. Another domain: await" check=run
@MainActor
final class ScoreBoard {
    var score = 0
    func add(_ points: Int) { score += points }
}

@MainActor
func tapButton(_ board: ScoreBoard) {
    board.add(1)                       // same actor: call it directly
}

func syncFromServer(_ board: ScoreBoard) async {   // belongs to no actor
    await board.add(10)                // a different actor: hop over with await
}

let board = ScoreBoard()
tapButton(board)                       // top-level code already runs on the main actor
await syncFromServer(board)
print("Score:", board.score)
```

Forget the `await`, and the compiler stops you:

```swift title="Calling into the main actor without await" check=error hl="8"
@MainActor
final class ScoreBoard {
    var score = 0
    func add(_ points: Int) { score += points }
}

func syncFromServer(_ board: ScoreBoard) async {
    board.add(10)
}
```

- A `@MainActor` class is `Sendable`: the main actor protects its state, so it can be shared freely.
- SwiftUI views and UIKit view controllers are already `@MainActor`, and so is top-level code in `main.swift`.
- `Task { }` started on the main actor runs on the main actor. That makes it the usual way to start async work from a button tap.
- [Swift 6.2](#f-default-isolation) can make `@MainActor` the default for a whole module, so you don't have to write it everywhere.

::: quiz
? A function that belongs to no actor calls a method on a `@MainActor` class. What does it need to write?
- Nothing: the method moves itself to the main thread
+ `await`, because the call crosses into the main actor
- `DispatchQueue.main.async { }` around the call
> A call into another isolation domain is asynchronous: the caller hops onto the main actor, waiting if the main actor is busy. In Swift 6 mode the compiler checks this for you.
:::

## sendable
title: "`Sendable`: what may cross between isolation domains"
line: 1
se: 0302
since: 5.5
level: core
short: Sendable
tags: Sendable @Sendable closure isolation domain boundary data race value type struct final class unchecked
tldr: Each actor, and the code that belongs to no actor, is its own **isolation domain**. A value may cross from one domain into another only if it's `Sendable`, meaning safe to use from both sides at once. Value types usually are; classes with mutable state aren't.

An actor protects its own state, but what about the values you pass in and out? Hand a mutable class instance to an actor and keep using it yourself, and two domains share one object: a data race again. In Swift 6 mode the compiler catches it:

```swift title="Sending a mutable object and still using it" check=error hl="12,13"
final class Draft {                     // a class with mutable state: not Sendable
    var text = ""
}

actor Outbox {
    func send(_ draft: Draft) { print("Sending:", draft.text) }
}

func compose(using outbox: Outbox) async {
    let draft = Draft()
    draft.text = "Hello"
    await outbox.send(draft)             // hand it to the actor's domain…
    draft.text = "Changed my mind"       // …while still changing it here
}
```

Make `Draft` a `struct` and the problem disappears: the actor gets its own copy, and each side changes only its own:

```swift title="A value type is copied: each domain gets its own" check=ok
struct Draft {                          // a value type: Sendable automatically
    var text = ""
}

actor Outbox {
    func send(_ draft: Draft) { print("Sending:", draft.text) }
}

func compose(using outbox: Outbox) async {
    var draft = Draft()
    draft.text = "Hello"
    await outbox.send(draft)             // the actor gets its own copy
    draft.text = "Changed my mind"       // changes only our copy
}
```

If `compose` never touched `draft` after sending it, even the class version would compile, because Swift 6 can prove that nobody else uses it any more. That's [6.0's region-based isolation](#f-region-sending).

Which types are `Sendable`?

| Type | Sendable? |
| --- | --- |
| `Int`, `String`, `Bool`, … | Yes |
| Arrays, dictionaries, and optionals of Sendable values | Yes |
| A `struct` or `enum` whose stored properties are all Sendable | Yes. Inferred inside the module; `public` types must declare it |
| An `actor`, or a `@MainActor` class | Yes: the actor protects the state |
| A `final class` whose stored properties are all Sendable `let`s | Yes, once it declares `: Sendable` |
| A class with a `var` stored property | No |

Closures cross domains too. A closure type marked `@Sendable` may run concurrently with other code, so it can't modify the local variables it captures:

```swift title="A @Sendable closure can't mutate what it captures" check=error hl="4"
func countClicks() {
    var clicks = 0
    let onClick: @Sendable () -> Void = {   // may run concurrently with other code
        clicks += 1
    }
    onClick()
}
```

- `@unchecked Sendable` tells the compiler “trust me, I synchronize this myself”, for example with a lock. The compiler then stops checking that type, so use it sparingly; 6.0's [`Mutex`](#f-synchronization) usually makes it unnecessary.
- The checks arrived gradually: 5.5 introduced the protocol, later 5.x releases added the checks as warnings (with `-strict-concurrency=complete`), and Swift 6 language mode makes them errors. That's [6.0's first station](#f-swift6-mode).

::: note Trying these in Xcode?
The examples here are compiled in Swift 6 language mode. In a target that is still set to Swift 5 mode, the errors on this page are only warnings, or don't appear at all. Check **Swift Language Version** in the build settings.
:::

::: quiz
? Which of these types is **not** `Sendable`?
- `struct Point { var x: Int; var y: Int }`
- `actor Store { var items: [String] = [] }`
+ `final class Box { var value = 0 }`
- `[String: Int]`
> Value types made of Sendable parts are Sendable, and actors protect themselves. A class with a mutable `var` can be changed from two domains at once, so it isn't Sendable unless it guards that state itself (by being an actor, by using a `Mutex`, …).
:::

## where-async-runs
title: Where does an async function run?
line: 1
se: 0338
since: 5.7
level: key
short: Where it runs
tags: executor global concurrent executor thread pool hop isolation nonisolated async main thread
tldr: An async function runs according to its **isolation**: an actor's method on that actor, a `@MainActor` function on the main thread, and a function that belongs to no actor on the **global concurrent pool**. A call that changes isolation is a “hop”.

Synchronous functions run on whatever thread calls them. Async functions are different: where they run is decided by their own isolation, not by the caller. Watch the main thread being left and re-entered:

```swift title="A nonisolated async function leaves the main actor" check=run expect="work() runs on a pool thread"
import Foundation

func whereAmI() -> String { Thread.isMainThread ? "the main thread" : "a pool thread" }

func work() async {                               // belongs to no actor
    print("  work() runs on", whereAmI())
}

@MainActor
func start() async {
    print("start() runs on", whereAmI())
    await work()                                  // hop: leave the main actor
    print("start() resumes on", whereAmI())      // hop back
}

await start()
```

This rule comes from SE-0338, in Swift 5.7. Before that, such a function kept running on whichever actor called it, which could tie up the main actor with work that was meant for the background. Since 5.7, a function that belongs to no actor always runs on the global concurrent pool, a set of threads shared by all tasks.

The rule is predictable, but it has a cost: everything you pass to `work()` crosses from the main actor into another domain, so it has to be [`Sendable`](#f-sendable). That's where many Swift 6 errors come from, and why Swift 6.2 lets you flip the default. Here's the same code with 6.2's upcoming feature turned on:

```swift title="The same code with NonisolatedNonsendingByDefault (Swift 6.2)" check=run flags="-swift-version 6 -enable-upcoming-feature NonisolatedNonsendingByDefault" expect="work() runs on the main thread"
import Foundation

func whereAmI() -> String { Thread.isMainThread ? "the main thread" : "a pool thread" }

func work() async {                               // belongs to no actor
    print("  work() runs on", whereAmI())
}

@MainActor
func start() async {
    print("start() runs on", whereAmI())
    await work()                                  // now stays with its caller
    print("start() resumes on", whereAmI())
}

await start()
```

- A hop is cheap but not free. More importantly, every hop is a boundary that values have to cross safely.
- Under the new default, mark a function [`@concurrent`](#f-concurrent) to keep the old behavior; without the upcoming feature, write [`nonisolated(nonsending)`](#f-nonsending) to get the new behavior one function at a time.
- Step through both rules in the [Concurrency Trace lab](#lab-concurrency).

::: note Trying this in Xcode?
New app projects in Xcode 26 turn on **Approachable Concurrency**, which includes `NonisolatedNonsendingByDefault`. In such a project the first example also prints “the main thread” for `work()`: you're seeing the 6.2 rule.
:::

::: quiz
? With no upcoming features on, a `@MainActor` function awaits an `async` function that belongs to no actor. Where does that function's code run?
- On the main thread, like its caller
+ On the global concurrent pool
- On a new thread created for that call
> Since SE-0338, a function that belongs to no actor runs on the global concurrent executor, a pool of threads shared by all tasks; no thread is created per call. 6.2's `nonisolated(nonsending)` lets it stay on the caller's actor instead.
:::

## checked-continuation
title: "Continuations: wrap a callback API in `async`"
line: 1
se: 0300
since: 5.5
level: brief
short: Continuations
tags: continuation withCheckedContinuation withCheckedThrowingContinuation CheckedContinuation resume callback completion handler bridge legacy
tldr: "`withCheckedContinuation` turns a completion-handler API into an `async` function: the task pauses until the callback calls `resume`, which must happen **exactly once**."

```swift title="From a completion handler to await" check=run
import Foundation

// An older API that reports its result through a completion handler
func legacyFetch(_ id: Int, completion: @escaping @Sendable (String) -> Void) {
    DispatchQueue.global().asyncAfter(deadline: .now() + 0.1) {
        completion("record #\(id)")
    }
}

func fetch(_ id: Int) async -> String {
    await withCheckedContinuation { continuation in
        legacyFetch(id) { value in
            continuation.resume(returning: value)   // resume exactly once
        }
    }
}

print(await fetch(7))
```

- For APIs that can fail, use `withCheckedThrowingContinuation` and `resume(throwing:)`.
- “Checked” means misuse is caught at run time: resuming twice crashes the program, and a continuation that is dropped without being resumed logs a warning, because the task waiting for it would otherwise hang forever.
- [6.4's `Continuation`](#f-continuation) turns “resumed twice” into a compile-time error.

## borrowing-consuming
title: "`consume`, `borrowing`, and `consuming`: say who owns a value"
line: 2
se: 0366, 0377
since: 5.9
level: key
short: borrowing · consuming
tags: ownership consume borrowing consuming copy move lifetime copy-on-write performance parameter modifier noncopyable deinit
tldr: Swift copies values and retains references wherever it needs to, without asking. Swift 5.9 lets you say it yourself: `consume x` ends a variable's lifetime and hands its value on, a `borrowing` parameter only reads the caller's value, and a `consuming` parameter takes it over.

Most of the time you don't think about ownership: an argument is either borrowed (the function reads it and the caller keeps it) or copied, and copy-on-write keeps copies cheap. Where every copy counts, and for the [noncopyable types](#f-noncopyable-generics) of 6.0, which can't be copied at all, you need to spell it out.

`consume` ends a local variable's lifetime right where you write it, and moves its value on. Here the connection closes the moment it's consumed, not at the end of the function:

```swift title="consume ends a lifetime early" check=run
final class Connection {
    let name: String
    init(_ name: String) { self.name = name; print("Open", name) }
    deinit { print("Close", name) }
}

func work() {
    let connection = Connection("db")
    print("Query on", connection.name)
    _ = consume connection          // the lifetime ends here, not at the closing brace
    print("Other work")
}
work()
```

After `consume`, the variable is gone, and using it again is a compile error:

```swift title="Used after consume" check=error hl="8,9"
final class Connection {
    let name: String
    init(_ name: String) { self.name = name }
}

func work() {
    let connection = Connection("db")
    _ = consume connection
    print(connection.name)
}
```

### Parameters say what happens to an argument

| Modifier | The function | The caller |
| --- | --- | --- |
| `borrowing` | only reads the value | keeps it |
| `consuming` | takes the value over: it may change it, store it, or pass it on | gives it up, unless it passes a copy |
| `inout` | changes the caller's value in place | sees the change |

Without a modifier Swift chooses for you: most parameters are borrowed, while the parameters of initializers and setters are consumed, since those usually store the value. Writing `borrowing` or `consuming` yourself also switches off implicit copies of that parameter, so every copy inside the function has to be written as `copy`:

```swift title="A borrowed parameter isn't copied behind your back" check=error hl="2"
func longestFirst(_ names: borrowing [String]) -> [String] {
    var sorted = names
    sorted.sort { $0.count > $1.count }
    return sorted
}
```

Write `var sorted = copy names`, and it compiles. A `consuming` parameter, on the other hand, belongs to the function. If the caller hands over its only reference with `consume`, an array can grow in place instead of being copied first:

```swift title="consume + consuming: the storage moves instead of being copied" check=run
func storage(of array: [Int]) -> UnsafeRawPointer? {     // where the array keeps its elements
    array.withUnsafeBufferPointer { UnsafeRawPointer($0.baseAddress) }
}

func appending(_ x: Int, to array: consuming [Int]) -> [Int] {
    array.append(x)               // the function owns `array`, so it may change it
    return array
}

func demo() {
    var numbers = Array(1...1_000)
    numbers.reserveCapacity(2_000)
    let before = storage(of: numbers)

    let a = appending(1_001, to: numbers)            // `numbers` is still used below: append must copy
    print("Without consume, same storage:", storage(of: a) == before)

    let b = appending(1_001, to: consume numbers)    // hand over the only reference
    print("With consume, same storage:", storage(of: b) == before)
}
demo()
```

- Methods can be `borrowing`, `consuming`, or `mutating` too; the modifier then applies to `self`. A `consuming func` uses up the value it's called on, like the ticket in [6.0's first ownership station](#f-noncopyable-generics).
- `consume` works on local variables and parameters, not on globals or stored properties. Top-level variables in `main.swift` are globals, which is why these examples sit inside a function.
- For ordinary types, reach for these only when a profile shows copies or retain/release traffic in hot code. Noncopyable types (`~Copyable`, also new in 5.9 with SE-0390) can't be copied at all, so there the modifiers are required, and 6.0 builds on them.
- Try it hands-on in the [Ownership Sandbox](#lab-ownership).

::: quiz
? `connection` holds a class instance. What does `_ = consume connection` do?
- It copies the object and releases the copy
+ It ends the variable's lifetime at that line, and any later use of `connection` is a compile error
- It destroys the object even if other references to it still exist
> `consume` ends a binding's lifetime, not an object's. In the example `connection` was the only reference, so the object was released at that line; if another variable still referred to it, the object would stay alive.
:::

## some-any
title: "`some` and `any`: one hidden type, or a box for any type"
line: 3
se: 0335, 0341, 0346
since: 5.7
level: core
short: some · any
tags: some any opaque type existential protocol generic box primary associated type Collection<Int> ExistentialAny implicitly opened
tldr: "`some Shape` stands for **one** concrete type that conforms to `Shape`: the compiler knows which, you just don't write it. `any Shape` is a **box** that can hold a value of any conforming type, a different one each time. Use `some` by default, and `any` when you need to mix types."

Using a protocol as a type has always been possible in Swift. Swift 5.6 lets you write that as `any Shape` (SE-0335), and 5.7 lets you write `some Shape` for parameters too, not only for return types (SE-0341). The difference shows as soon as you use both:

```swift title="some: one type per call. any: a mix of types" check=run
protocol Shape {
    func area() -> Double
}

struct Square: Shape {
    var side: Double
    func area() -> Double { side * side }
}

struct Circle: Shape {
    var radius: Double
    func area() -> Double { 3.14 * radius * radius }
}

func describe(_ shape: some Shape) -> String {     // one concrete type per call, known at compile time
    "\(type(of: shape)) with area \(shape.area())"
}

let shapes: [any Shape] = [Square(side: 2), Circle(radius: 1)]   // boxes that can hold any Shape
for shape in shapes {
    print(describe(shape))                         // each box is opened for the call
}
```

`some Shape` as a parameter is shorthand for a generic parameter: `func describe<S: Shape>(_ shape: S)`. As a return type it promises that the function always returns the same type, which callers don't get to see. That's what SwiftUI's `some View` means, and it's why this doesn't compile:

```swift title="some: the same type on every path" check=error hl="15,17"
protocol Shape {
    func area() -> Double
}
struct Square: Shape {
    var side: Double
    func area() -> Double { side * side }
}
struct Circle: Shape {
    var radius: Double
    func area() -> Double { 3.14 * radius * radius }
}

func makeShape(round: Bool) -> some Shape {
    if round {
        return Circle(radius: 1)
    }
    return Square(side: 1)
}
```

If the function really has to return different types, make the return type `any Shape`.

Protocols such as `Collection` and `Sequence` declare a **primary associated type** in angle brackets (SE-0346), so `some` and `any` can also say what's inside:

```swift title="some Collection<Int>" check=run
func total(_ numbers: some Collection<Int>) -> Int {     // any collection, as long as it holds Ints
    numbers.reduce(0, +)
}

print(total([1, 2, 3]))
print(total(1...10))
print(total(Set([5, 6])))
```

- `any` has a cost. The box adds indirection (a large value lives on the heap), calls go through a table, and the concrete type is lost: two `any Equatable` values can't even be compared with `==`. `some` keeps the type and compiles like a generic.
- Passing an `any Shape` to a `some Shape` parameter opens the box automatically (SE-0352, Swift 5.7), as the loop in the first example does.
- In Swift 6 mode a bare `Shape` still means `any Shape`. The upcoming feature `ExistentialAny` makes the `any` required: see the [last station of this zone](#f-upcoming-features).
- Later stations use both: `throws` is short for `throws(any Error)` in [6.0's typed throws](#f-typed-throws), `#isolation` has the type `(any Actor)?` in [6.0](#f-isolation-inherit), and [6.4](#f-optional-some) lets you write `some Shape?`.

::: quiz
? Which type lets one array hold both a `Square` and a `Circle`?
- `[some Shape]`
+ `[any Shape]`
- `[Shape.Type]`
> `some Shape` is a single concrete type, so every element of `[some Shape]` would have to be that same type. `any Shape` boxes each value, and each box can hold a different type.
:::

## macros
title: "Macros: `#` and `@` that write code for you"
line: 3
se: 0382, 0389, 0397
since: 5.9
level: key
short: Macros
tags: macro macros freestanding attached expression declaration accessor peer member expansion Expand Macro dump-macro-expansions swift-syntax compiler plugin externalMacro TaskLocal Observable Test expect Playground
tldr: A macro writes ordinary Swift code for you at compile time. **Freestanding** macros start with `#` and stand on their own, like `#expect(…)`; **attached** macros start with `@` and add to the declaration they're attached to, like `@Observable`. What they write is plain Swift that you can expand and read.

Many newer APIs on this map are macros: Swift Testing's `@Test` and `#expect`, `@Observable`, `@DebugDescription`, `#isolation`, and the `#Playground` you might be pasting these examples into. A macro is like a function that runs inside the compiler: it receives your code as a syntax tree and returns more code, which is compiled along with yours.

You can always look at that code. In Xcode, right-click a macro and choose **Expand Macro**; on the command line, the flag `-dump-macro-expansions` prints it. Here is the standard library's `@TaskLocal` macro, which turns a static property into a per-task value: `withValue` sets it for all the code that runs inside its closure.

```swift title="What @TaskLocal writes" check=run flags="-swift-version 6 -Xfrontend -dump-macro-expansions"
enum Request {
    @TaskLocal static var id = "none"
}

func log(_ message: String) {
    print("[\(Request.id)] \(message)")
}

func handle() {
    Request.$id.withValue("A-42") {       // `$id` was written by the macro
        log("handling")
    }
    log("idle")
}

handle()
```

The macro added two pieces: a getter for `id` (an **accessor** macro), and next to it a `$id` property that holds the actual `TaskLocal` value (a **peer** macro). Neither appears in the source.

| Kind | Written as | Examples | What it adds |
| --- | --- | --- | --- |
| Freestanding expression macro | `#name(…)` | `#expect(x == 1)`, `#isolation` | An expression, in place of the macro |
| Freestanding declaration macro | `#name(…)` | `#Playground { … }`, `#Preview { … }` | New declarations |
| Attached macro | `@Name` before a declaration | `@Observable`, `@Test`, `@TaskLocal` | Members, accessors, peers, extensions, conformances |

A macro is declared with the keyword `macro`, much like a function, and names the module that implements it. This is how Xcode's Playgrounds module declares `#Playground`:

```swift title="The declaration of #Playground in Xcode's Playgrounds module" check=none
@freestanding(declaration)
public macro Playground(
    _ name: String? = nil,
    body: @escaping @Sendable () async throws -> Void
) = #externalMacro(module: "PlaygroundMacros", type: "Playground")
```

The implementation, the type `Playground` in the module `PlaygroundMacros`, is a separate program built with the swift-syntax library, which the compiler runs as a plugin. Its expansion passes your closure on as a `@MainActor` async closure, which is why the code in a `#Playground` block runs on the main actor and can use `await`. Macro packages that you add with SwiftPM work the same way; `swift package init --type macro` creates one.

- A macro's arguments must type-check before it runs, and what it writes is type-checked again. Unlike a C preprocessor macro, a Swift macro works on syntax trees, not on text.
- Macros only add code: they never edit or delete what you wrote.
- Macro plugins run in a sandbox, with no access to the network or your files. The first time you build a package that uses someone else's macros, Xcode asks you to trust them.
- Coming up: [`@Observable`](#f-observable) two stations ahead, then in 6.0 [Swift Testing](#f-swift-testing), [`@DebugDescription`](#f-debug-description), and [`#isolation`](#f-isolation-inherit).

::: note Trying this in a Playground?
Put the declarations above `#Playground { }` and only call `handle()` inside it. The block is itself a macro's argument, and in there Swift 6.4 doesn't find names that other macros wrote, such as `$id`.
:::

::: quiz
? What does an attached macro such as `@Observable` do to the class it's written on?
- It edits the class's source file before compiling it
+ It adds ordinary Swift code to it (members, accessors, conformances) that you can expand and read
- It changes the class's behavior at run time, through reflection
> Macros run at compile time. They receive the declaration as a syntax tree and add code to it, never edit it, and the result is compiled like any other Swift. Expand Macro in Xcode shows you what was added.
:::

## parameter-packs
title: "Parameter packs: generics over any number of types"
line: 3
se: 0393, 0398, 0399
since: 5.9
level: brief
short: Parameter packs
tags: parameter pack variadic generics each repeat pack expansion tuple overloads ViewBuilder buildBlock
tldr: "`<each T>` declares a **type parameter pack**: any number of generic types, each of which may be different. `repeat` expands a pattern once per element, so one generic function can replace a stack of overloads for 2, 3, 4… arguments."

A variadic parameter `T...` accepts any number of values, but they must all be the same type. Functions that combine values of different types used to be written as one overload per count: SwiftUI's view builder had versions for 1 to 10 views. Today's SDK declares a single `buildBlock<each Content>` instead. With a pack, each argument keeps its own type:

```swift title="One function, any number of differently typed arguments" check=run
func describe<each Value>(_ value: repeat each Value) -> [String] {
    var lines: [String] = []
    repeat lines.append(String(describing: each value))    // runs once per argument
    return lines
}

print(describe(42, "Swift", 6.4, true))
print(describe())

func duplicate<each T>(_ value: repeat each T) -> (repeat (each T, each T)) {
    (repeat (each value, each value))
}

let pairs = duplicate(1, "a", true)
print(pairs)
print(type(of: pairs))                  // every type is kept: no Any anywhere
```

- `each T` refers to the pack; `repeat` marks a **pattern** that is expanded once per element, so `repeat (each T, each T)` becomes `(Int, Int), (String, String), (Bool, Bool)`.
- Types can take packs too (SE-0398), as in `struct Row<each Column>`.
- [6.0](#f-pack-iteration) adds `for … in repeat each`, which makes packs much easier to loop over.

## observable
title: "`@Observable`: classes that report what changed"
line: 4
se: 0395
since: 5.9
level: key
short: "@Observable"
tags: Observation Observable withObservationTracking ObservationIgnored ObservableObject Published SwiftUI State Bindable tracking change
tldr: Mark a class `@Observable` and reads of its properties can be tracked. `withObservationTracking` runs a closure, notes which properties it read, and calls you back when one of **those** is about to change. That's how SwiftUI decides which views to redraw.

Before Swift 5.9, a SwiftUI model was an `ObservableObject` with `@Published` on each property, and a view redrew whenever any of them changed, even one it never read:

```swift title="Before: ObservableObject and @Published" check=ok
import Combine

final class Cart: ObservableObject {
    @Published var items: [String] = []
    @Published var coupon: String?
}
```

The Observation module replaces that with a macro: no property wrappers, and tracking is per property:

```swift title="Only the properties you read are tracked" check=run
import Observation

@Observable
final class Cart {
    var items: [String] = []
    var coupon: String?
}

let cart = Cart()

withObservationTracking {
    print("Showing", cart.items.count, "items")     // reads only `items`
} onChange: {
    print("items is about to change")
}

cart.coupon = "SAVE10"          // not read above: no call
cart.items.append("Book")       // calls onChange, once
cart.items.append("Pen")        // it already fired: no call
print("Now", cart.items)
```

- `onChange` runs **before** the change, and only once. To keep watching you have to call `withObservationTracking` again: [6.2's `Observations`](#f-observations) wraps that up as an async sequence, and [6.4](#f-observation-tracking) adds options to the function itself.
- `@Observable` works on classes only; on a struct, the macro reports an error. Mark a property `@ObservationIgnored` to leave it out of tracking.
- Expand the macro (see the [macros station](#f-macros)) to see what it writes: a hidden `_$observationRegistrar`, and accessors that report each read and write to it.
- In SwiftUI, keep an `@Observable` model in `@State` instead of `@StateObject`, and pass it to child views as a plain property; `@Bindable` makes bindings to its properties.

::: note Trying this in a Playground?
Declare `Cart` above `#Playground { }`, at the top level of the file. `@Observable` adds its conformance with an extension macro, and a type declared inside the block is a local type, which can't have one.
:::

::: quiz
? A view's `body` reads `cart.items` but never `cart.coupon`. With an `@Observable` `Cart`, what happens when `coupon` changes?
- The view redraws, like any `ObservableObject` view would
+ Nothing: the view only tracks the properties its `body` actually read
- The app crashes, because `coupon` wasn't registered
> Observation tracks per property. SwiftUI runs `body` inside tracking, so only changes to `items` invalidate this view. With `ObservableObject`, any `@Published` change would have.
:::

## clock-duration
title: "`Duration` and clocks: time as a type"
line: 4
se: 0329
since: 5.7
level: brief
short: Duration · Clock
tags: Duration Clock ContinuousClock SuspendingClock Instant measure sleep time timeout seconds milliseconds deadline
tldr: "`Duration` is a span of time with its unit, such as `.seconds(2)` or `.milliseconds(250)`, that you can add, compare, and divide. A clock tells the time: `ContinuousClock().now` is an `Instant`, and subtracting two instants gives a `Duration`."

```swift title="Durations, instants, and measuring" check=run
let timeout: Duration = .seconds(2) + .milliseconds(500)
print(timeout, timeout / 5, timeout > .seconds(2))

let clock = ContinuousClock()
let elapsed = await clock.measure {               // how long did the closure take?
    try? await Task.sleep(for: .milliseconds(120))
}
print(elapsed >= .milliseconds(120))

let start = clock.now                             // an Instant: a point in time on this clock
try await clock.sleep(until: start + .milliseconds(50))
print(clock.now - start >= .milliseconds(50))     // Instant − Instant = Duration
```

- `Task.sleep(for:)`, used all through the concurrency stations, takes a `Duration`. The older `Task.sleep(nanoseconds:)` took a bare `UInt64`.
- Dividing a `Duration` by a `Duration` gives a `Double`: `elapsed / .milliseconds(1)` is the time in milliseconds. That's how the [`async let` station](#f-structured) times its fetches.
- `ContinuousClock` keeps counting while the device sleeps; `SuspendingClock` stops with it. Use the continuous clock for timeouts and deadlines in the real world.
- [6.3](#f-clock-epochs) gives both clocks a `systemEpoch`.

## upcoming-features
title: "Upcoming features: tomorrow's rules, one at a time"
line: 6
se: 0362
since: 5.8
level: key
short: Upcoming features
tags: upcoming feature flag enable-upcoming-feature enableUpcomingFeature hasFeature language mode Swift 6 ExistentialAny Approachable Concurrency migration source compatibility
tldr: Changes that would break existing code wait for the next **language mode**. Each also gets a name, such as `ExistentialAny`, and since Swift 5.8 you can switch on just that change with `-enable-upcoming-feature`. Stations on this map that need one show its name in a chip.

A language mode decides which rules your code is compiled with; the compiler version doesn't. Swift 6 mode is largely a bundle of such changes, collected one at a time over the 5.x releases. Code can check whether one is on with `#if hasFeature(…)`:

```swift title="Which features is this code compiled with?" check=run
#if hasFeature(StrictConcurrency)
print("StrictConcurrency               on")
#else
print("StrictConcurrency               off")
#endif

#if hasFeature(ExistentialAny)
print("ExistentialAny                  on")
#else
print("ExistentialAny                  off")
#endif

#if hasFeature(NonisolatedNonsendingByDefault)
print("NonisolatedNonsendingByDefault  on")
#else
print("NonisolatedNonsendingByDefault  off")
#endif
```

Swift 6 mode includes `StrictConcurrency` and 14 other upcoming features. The other two in this list aren't part of Swift 6 mode, so they stay off until you switch them on. Once you do, you get their rules today. `ExistentialAny`, for example, flags every protocol used as a type without `any`:

```swift title="Switch on ExistentialAny" check=warning flags="-swift-version 6 -enable-upcoming-feature ExistentialAny" hl="5"
protocol Shape {
    func area() -> Double
}

func totalArea(_ shapes: [Shape]) -> Double {
    shapes.reduce(0) { $0 + $1.area() }
}
```

In a package, list the features per target:

```swift file=Package.swift check=none
// swift-tools-version: 6.0
import PackageDescription

let package = Package(
    name: "MyApp",
    targets: [
        .target(
            name: "Core",
            swiftSettings: [
                .enableUpcomingFeature("ExistentialAny"),
                .enableUpcomingFeature("InternalImportsByDefault"),
            ]
        ),
    ]
)
```

### Still to come

Swift 6.4's compiler knows six upcoming features that Swift 6 mode doesn't include (`swiftc -print-supported-features` lists them). Each one has a station on this map:

| Upcoming feature | What it changes | Station |
| --- | --- | --- |
| `ExistentialAny` | A protocol used as a type must be written `any P` | [`some` and `any`](#f-some-any) |
| `InternalImportsByDefault` | A plain `import` means `internal import` | [6.0](#f-import-access) |
| `MemberImportVisibility` | Members from extensions are only visible in files that import their module | [6.1](#f-member-import) |
| `InferIsolatedConformances` | Conformances of a `@MainActor` type are isolated to the main actor | [6.2](#f-isolated-conformances) |
| `NonisolatedNonsendingByDefault` | Nonisolated async functions run on the caller's actor | [6.2](#f-nonsending) |
| `ImmutableWeakCaptures` | Variables captured with `[weak x]` can't be reassigned | [6.3](#f-weak-let) |

- In Xcode the features are build settings, under **Swift Compiler - Upcoming Features**. Xcode 26's **Approachable Concurrency** setting switches on a group of them, including `NonisolatedNonsendingByDefault` and `InferIsolatedConformances`, so in a new Xcode 26 project the first example prints `on` for `NonisolatedNonsendingByDefault`.
- `-enable-experimental-feature` is a different thing: unfinished features that can still change or disappear.
- [6.2's `swift package migrate`](#f-swiftpm-62) can make the edits a feature needs for you.
- The next stop is [6.0](#f-swift6-mode), whose first station switches on the whole Swift 6 mode.
