## c-interop
title: "`@c`: let C call Swift directly"
line: 5
se: 0495
level: core
short: "@c"
tags: C interop cdecl @_cdecl header embedded FFI @implementation
tldr: Add `@c` to a global function or enum and the compiler generates it with the C calling convention and writes its declaration into the generated header, so C/C++ code can simply `#include` it and call it. It replaces the long-“unofficial” `@_cdecl`.

```swift title="MathKit.swift" check=ok
@c(MathKit_clamp)                       // you can pick the name on the C side
public func clamp(_ value: CInt, _ low: CInt, _ high: CInt) -> CInt {
    min(max(value, low), high)
}

@c
public enum Direction: CInt {           // must have a C-compatible integer raw value type
    case north, south
}
```

```c title="The header the compiler generates (an excerpt of real output, from swiftc -emit-clang-header-path)" check=none
typedef SWIFT_ENUM(int, Direction, closed) {
  DirectionNorth = 0,
  DirectionSouth = 1,
};

SWIFT_EXTERN int MathKit_clamp(int value, int low, int high) SWIFT_NOEXCEPT SWIFT_WARN_UNUSED_RESULT;
```

In the other direction, if a C header **already has** a function declaration, you can write its implementation in Swift with `@c @implementation`. The compiler checks that the signatures on both sides match:

```c title="geometry.h: an existing C declaration" check=none
double area_of_circle(double radius);
```

```swift title="geometry.swift: implemented in Swift" check=none
@c @implementation
func area_of_circle(_ radius: Double) -> Double {
    .pi * radius * radius
}
```

- An enum case becomes “type name + capitalized case name” on the C side, such as `DirectionNorth`.
- The same release also allows `@objc` on global functions, whose signatures can use Objective-C types.
- Recommended pattern: wrap a safe Swift API around the `@c` function, for example taking a `Span` instead of a pointer plus a length (the 6.4 release notes specifically recommend this).

## module-selectors
title: "Module selectors `Module::name`"
line: 3
se: 0491
level: key
short: Module selectors
tags: module selector module name clash :: same name ambiguity disambiguation
tldr: Two imported modules both have an API with the same name? Write `ModuleA::getValue()` to say exactly which module to look in. When your own type shares a name with a standard library one, `Swift::` gets you the standard library's.

```swift title="Your own Task has the same name as the standard library's" check=run
struct Task {
    var title: String
}

let todo = Task(title: "Write weekly report")      // our own Task

let job = Swift::Task {                            // the standard library's concurrency Task
    print("Working in the background:", todo.title)
}
await job.value
```

Before, the only way out of such a clash was `Swift.Task`. But if some module happens to have a type called `Swift`, or a module has the same name as one of its types (such as `XCTest.XCTest`), dot syntax breaks down. `::` always and only means “module”, so there is no ambiguity:

```swift check=none
import ModuleA
import ModuleB

let x = ModuleA::getValue()     // calls ModuleA's getValue
let y = ModuleB::getValue()     // calls ModuleB's getValue
```

## perf-attrs
title: "Three optimization wrenches for library authors: `@specialized`, `@inline(always)`, `@export`"
line: 2
se: 0460, 0496, 0497
level: key
short: Optimization control
tags: specialize specialized inline always export implementation interface optimization generics library performance
tldr: Three attributes that let a library's author control how the compiler optimizes “code that calls me”: pre-generate specialized versions of generics, guarantee inlining, and expose a function's implementation to callers.

```swift check=ok
extension Sequence where Element: BinaryInteger {
    @specialized(where Self == [Int])        // pre-generate a specialization for [Int]
    @specialized(where Self == [UInt8])
    public func total() -> Int {
        reduce(0) { $0 + Int($1) }
    }
}

@inline(always)                              // guarantee that every direct call site is inlined
public func fastAbs(_ x: Int) -> Int {
    x < 0 ? -x : x
}

@export(implementation)                      // provide the body to callers, enabling cross-module optimization
public func clampPercent(_ x: Double) -> Double {
    min(max(x, 0), 100)
}
```

| Attribute | What it does | Replaces |
| --- | --- | --- |
| `@specialized(where …)` | Pre-generates generic specializations for common types in the library; the generic version checks the type at its entry and forwards to the specialization | `@_specialize` |
| `@inline(always)` | Guarantees a direct call is inlined; if it can't be done, it's an error rather than silently ignored | `@inline(__always)` |
| `@export(implementation)` | The function body is visible to callers, which can inline and specialize it | `@_alwaysEmitIntoClient` |
| `@export(interface)` | Exports only a callable symbol and hides the implementation | `@_neverEmitIntoClient` |

These attributes mainly target authors of libraries that ship binary frameworks and chase peak performance. Application developers usually don't need to touch them; overusing `@inline(always)` only bloats code size.

## section
title: "`@section` and `@used`: put data into a specific section"
line: 2
se: 0492
level: brief
short: "@section"
tags: section linker used embedded plugin static initialization constant
tldr: Place a global variable in a named section of the object file, and use `@used` to stop the linker from deleting it as “unused”. Common in embedded development and “linker collection” style plugin registration.

```swift check=ok
#if objectFormat(MachO)
@section("__DATA,plugins")
#else
@section("plugins")
#endif
@used
let pluginVersion: Int = 3        // the initial value must be a compile-time constant
```

The new conditions `#if objectFormat(MachO)`, `objectFormat(ELF)`, and `objectFormat(COFF)` handle the different rules each object file format has for section names.

## weak-let
title: "`weak let`: immutable weak references"
line: 1
se: 0481
flag: ImmutableWeakCaptures
level: key
short: weak let
tags: weak let weak reference Sendable immutable retain cycle capture
tldr: Until now `weak` could only be paired with `var`, so a class with a weak property could never be `Sendable`. Now you can write `weak let`: it can't be changed after initialization, but it still becomes `nil` automatically when the object is released.

```swift title="Before: a weak var in a Sendable class is always an error" check=error
final class TreeNode: Sendable {
    weak var parent: TreeNode?

    init(parent: TreeNode?) {
        self.parent = parent
    }
}
```

```swift title="Swift 6.3: weak let" check=ok
final class TreeNode: Sendable {
    weak let parent: TreeNode?        // assigned only during initialization
    let name: String

    init(name: String, parent: TreeNode?) {
        self.name = name
        self.parent = parent
    }
}
```

The upcoming feature `ImmutableWeakCaptures` applies the same idea to closure captures: variables captured with `[weak self]` become immutable, so such closures can be `@Sendable`.

## clock-epochs
title: Clock epochs with `systemEpoch`
line: 4
se: 0473
level: brief
short: Clock epochs
tags: Clock ContinuousClock SuspendingClock epoch time Instant
tldr: "`ContinuousClock` and `SuspendingClock` gain a `systemEpoch` property, the “zero point” of that clock on this machine."

```swift check=run
let clock = ContinuousClock()
let sinceEpoch = clock.now - clock.systemEpoch
print(sinceEpoch > .zero)
```

The epoch is “system-dependent” and not comparable across machines, so it isn't suitable for serialization. It's useful for converting to and from other timing APIs on the system (such as kernel timestamps).

## codable-errors
title: A `DecodingError` that's easier to read

level: brief
short: Decoding errors

tldr: "`EncodingError` and `DecodingError` now conform to `CustomDebugStringConvertible`, and the message they print says clearly which field, what type was expected, and what was actually found."

```swift title="Below is the real printed result from Swift 6.4.2" check=run
import Foundation

struct User: Decodable {
    let name: String
    let age: Int
}

let json = Data(#"{"name": "Lin", "age": "eighteen"}"#.utf8)
do {
    _ = try JSONDecoder().decode(User.self, from: json)
```

## android
title: The official Swift SDK for Android
line: 5
level: key
short: Android
tags: Android SDK cross-compilation Kotlin Java JNI cross-platform
tldr: Swift 6.3 ships the first official Android SDK. You can write native Android apps in Swift, compile an existing Swift package for Android, or plug Swift code into an existing Kotlin/Java app through Swift Java and JNI.

This is the result of the Android workgroup moving the SDK from “nightly builds” to a proper release. Together with [6.1's package traits](#f-package-traits), one Swift package can turn features on or trim them depending on the platform. By [6.4](#f-interop-64), the Android SDK is built on an LTS NDK, and SwiftPM can build directly for Android through Swift Build.

In the same release, Embedded Swift improved its C interop and debugging support, and made progress on its linking model.

## testing-63
title: "Swift Testing: warning-level issues, test cancellation, and image attachments"
line: 6

short: Warnings & cancel
tags: Swift Testing Issue severity warning cancel cancellation attachment image
tldr: "`Issue.record(…, severity: .warning)` records a problem without failing the test; `try Test.cancel()` can cancel a running test midway; attachments support common image formats."

```swift check=ok testing
import Testing

@Test func slowButAcceptable() {
    Issue.record("Response took 1.8 s, a bit slow", severity: .warning)   // on record, but the test still passes
}

@Test(arguments: ["zh", "en", "ja"])
func localizedStrings(language: String) throws {
    if language == "ja" {
        try Test.cancel("Japanese resources aren't ready yet")    // cancels just this one argument case
    }
    #expect(!language.isEmpty)
}
```
