## swift6-mode
title: Swift 6 language mode: data races become compile errors
line: 1
se: 0337, 0412, 0414
level: core
short: Swift 6 mode
tags: data race Sendable strict concurrency language mode swiftLanguageModes migration complete concurrency checking
tldr: In Swift 6 language mode the compiler checks concurrency across the whole module: any data race that **might** happen is a compile error, not a crash that shows up only occasionally in production.

Swift 5.5 introduced `async`/`await` and actors, but concurrency checking has always been “advisory”: code with a data race could compile quietly. The Swift 6 compiler adds the **Swift 6 language mode**, in which `Sendable` checking and actor-isolation checking are all errors.

Here is a typical problem. A plain class is modified from two places that run concurrently:

```swift title="Swift 5 mode: compiles fine, but hides a data race" check=ok flags="-swift-version 5"
final class Counter {
    var value = 0
}

func race() {
    let counter = Counter()
    Task.detached {
        counter.value += 1      // write from a background thread
    }
    counter.value += 1          // write from the current thread at the same time
}
```

The same code in Swift 6 mode: the compiler points at the two conflicting accesses precisely:

```swift title="The same code, in Swift 6 mode" check=error flags="-swift-version 6" hl="7,10"
final class Counter {
    var value = 0
}

func race() {
    let counter = Counter()
    Task.detached {
        counter.value += 1      // write from a background thread
    }
    counter.value += 1          // write from the current thread at the same time
}
```

Global mutable state is another common problem: any thread can read and write a `static var` at any time. Swift 6 mode requires you to say who protects it:

```swift title="Global mutable state is stopped as well" check=error
struct Settings {
    static var current = Settings()
    var theme = "light"
}
```

```swift title="Three fixes, pick one" check=ok
struct Settings {
    static let standard = Settings()                    // ① make it an immutable let
    @MainActor static var current = Settings()          // ② let the main actor protect it
    nonisolated(unsafe) static var legacy = Settings()  // ③ you guarantee the synchronization yourself (use sparingly)
    var theme = "light"
}
```

### How to turn it on and how to migrate

The language mode and the compiler version are two different things: the Swift 6.0 through 6.4 compilers all support both Swift 5 and Swift 6 modes, so you can migrate target by target.

```swift file=Package.swift check=none
// swift-tools-version: 6.0
import PackageDescription

let package = Package(
    name: "MyApp",
    targets: [
        .target(name: "Core"),                           // tools-version 6.0: Swift 6 mode by default
        .target(
            name: "Legacy",
            swiftSettings: [.swiftLanguageMode(.v5)]     // this target stays in Swift 5 mode for now
        ),
    ]
)
```

- Before migrating, add `-strict-concurrency=complete` in Swift 5 mode to see the same problems as **warnings** ahead of time. Fix them one by one, then switch.
- In Xcode this corresponds to **Swift Language Version** in Build Settings.
- Don't sprinkle `@unchecked Sendable` or `nonisolated(unsafe)` everywhere right away: they only make the compiler be quiet, and the problem is still there.
- A lot of the work in the following releases (especially [6.2's “approachable concurrency”](#v62)) is about making Swift 6 mode nicer to use, with fewer errors.

::: quiz

+ It builds as usual: the project's language mode is still Swift 5, and complete checking only turns on once you switch to Swift 6 mode

> The new compiler keeps the project's existing language mode by default. Swift 6 mode must be turned on explicitly, and it can be turned on per target.

## region-sending
title: "Region-based isolation and `sending`: the compiler understands “handoffs”"
line: 1
se: 0414, 0430
level: core
short: sending
tags: region isolation region-based sending transferring Sendable non-Sendable handoff
tldr: A non-`Sendable` value can be handed to another task safely, as long as the compiler can prove you won't touch it afterwards. The `sending` keyword writes that “handoff” into a function signature.

Early strict-concurrency rules were rigid: if a type isn't `Sendable`, its values can't cross an isolation boundary, even when you just created an object and handed all of it to a background task.

SE-0414 introduced **region-based isolation**. The compiler tracks which “region” each value belongs to: if a region is handed off as a whole and never used again, the handoff is safe.

```swift title="Create an object, hand it to a background task, never touch it again: fine" check=ok
final class Report {
    var lines: [String] = []
}

func generate() {
    let report = Report()
    report.lines.append("Title")
    Task.detached {
        report.lines.append("Body")    // the whole region containing report is handed to this task
    }
    // report is never accessed again → compiles
}
```

```swift title="Using it after handing it off: the compiler pinpoints the conflict" check=error hl="11"
final class Report {
    var lines: [String] = []
}

func generate() {
    let report = Report()
    report.lines.append("Title")
    Task.detached {
        report.lines.append("Body")
    }
    report.lines.append("Footer")      // concurrent with the background task
}
```

### Writing the handoff into your API with `sending`

`Task.detached` accepts the closure above because its parameter is marked `sending`: the caller promises to hand the value off and never use it again. Your own functions can declare the same thing:

```swift title="A plain parameter belongs to the caller's region and can't be handed to another task" check=error
final class Photo {
    var pixels: [UInt8] = []
}

func process(_ photo: Photo) {
    Task.detached {
        photo.pixels.append(0)
    }
}
```

```swift title="Marked as sending: the caller hands over ownership" check=ok
final class Photo {
    var pixels: [UInt8] = []
}

func process(_ photo: sending Photo) {
    Task.detached {
        photo.pixels.append(0)        // ✅ photo is now disconnected from the caller
    }
}

func makePhoto() -> sending Photo {   // a return value can be sending too: a fresh value shared with no one
    Photo()
}

func upload() {
    process(makePhoto())
}
```

- Region-based isolation needs no code from you; it takes effect as soon as you upgrade the compiler. Many places that used to need an `@unchecked Sendable` workaround now compile directly.
- A `sending` parameter: the caller hands the value off, and the callee may hand it on to other isolation domains. A `sending` return value returns a “clean” fresh value.
- Early drafts of the proposal called it `transferring`; it was renamed `sending` in the end.

## synchronization
title: "`Mutex` and `Atomic`: synchronization primitives in the standard library"
line: 1
se: 0410, 0433
level: key
short: Mutex·Atomic
tags: Mutex Atomic lock Synchronization atomic thread-safe Sendable
tldr: The new `Synchronization` module provides `Mutex` and `Atomic`. Types that use them to protect their internal state can honestly be declared `Sendable`, with no `@unchecked`.

To write a thread-safe class you used to reach for `NSLock`, `os_unfair_lock`, or `DispatchQueue`, and then add `@unchecked Sendable` to tell the compiler “trust me”. Now the standard library provides locks and atomics directly, and the compiler understands their safety:

```swift title="Protect a cache with Mutex; the type can honestly declare Sendable" check=run
import Synchronization

final class ImageCache: Sendable {
    private let storage = Mutex<[String: Int]>([:])

    func insert(_ size: Int, for key: String) {
        storage.withLock { $0[key] = size }
    }

    func size(for key: String) -> Int? {
        storage.withLock { $0[key] }
    }
}

let cache = ImageCache()
cache.insert(1024, for: "avatar.png")
print(cache.size(for: "avatar.png") ?? 0)
```

```swift title="Atomic: a lock-free counter" check=run
import Synchronization

final class Stats: Sendable {
    let visits = Atomic<Int>(0)
}

let stats = Stats()
await withTaskGroup { group in
    for _ in 0..<100 {
        group.addTask { stats.visits.add(1, ordering: .relaxed) }
    }
}
print(stats.visits.load(ordering: .relaxed))
```

- `Mutex` and `Atomic` are both `~Copyable` (noncopyable) types: store them in `let` properties and access them by borrowing, so you can't accidentally copy out a second lock.
- They need the runtime that ships with macOS 15, iOS 18, and so on.
- Actors are still the first thing to consider in most cases; `Mutex` fits better in synchronous code, in performance-sensitive paths, or where you don't want to introduce an `await`.

## isolation-inherit
title: "`#isolation`: let a function inherit the caller's isolation"
line: 1
se: 0420, 0431
level: brief
short: "#isolation"
tags: isolation isolated parameter inherit actor isolated(any)
tldr: Add an `isolated (any Actor)? = #isolation` parameter to an async function and it runs on the caller's actor, so it can safely work with the caller's non-`Sendable` state.

```swift title="A timing helper that “follows the caller”" check=ok
func measure<T>(
    _ label: String,
    isolation: isolated (any Actor)? = #isolation,
    _ body: () async throws -> T
) async rethrows -> T {
    let start = ContinuousClock.now
    defer { print(label, ContinuousClock.now - start) }
    return try await body()
}

@MainActor
final class Feed {
    var items: [String] = []

    func reload() async {
        await measure("reload") {
            items = ["News A", "News B"]   // measure and the closure both run on the main actor
        }
    }
}
```

This spelling is a bit verbose: `(any Actor)?` is [a box for any actor](#f-some-any), or `nil` when the caller isn't isolated to one. In Swift 6.2, [`nonisolated(nonsending)`](#f-nonsending) makes “async functions inherit the caller's isolation” the default behavior, so most of the time you no longer need to write this parameter by hand. The same release also adds the `@isolated(any)` function type, which lets whoever holds a closure query its isolation (the `Task` initializers use it).

## typed-throws
title: "Typed throws: `throws(E)`"
line: 3
se: 0413
level: core
short: Typed throws
tags: typed throws error handling catch Never rethrows
tldr: A function can declare that it only throws one kind of error: `throws(ParseError)`. The caller's `catch` receives a `ParseError` directly, can `switch` over it exhaustively, and no longer has to guess the type with `as?`.

```swift title="Before: the catch only sees any Error" check=run
enum ParseError: Error {
    case empty
    case notANumber(String)
}

func parseAge(_ text: String) throws -> Int {
    guard !text.isEmpty else { throw ParseError.empty }
    guard let n = Int(text) else { throw ParseError.notANumber(text) }
    return n
}

do {
    _ = try parseAge("eighteen")
} catch let error as ParseError {     // you have to cast the type yourself
    print("Parse failed:", error)
} catch {
    print("Can't happen, but the compiler requires a fallback:", error)
}
```

```swift title="Now: throws(ParseError)" check=run hl="6,12-13,15-18"
enum ParseError: Error {
    case empty
    case notANumber(String)
}

func parseAge(_ text: String) throws(ParseError) -> Int {
    guard !text.isEmpty else { throw .empty }        // the type name can be omitted
    guard let n = Int(text) else { throw .notANumber(text) }
    return n
}

do throws(ParseError) {                              // state the error type this do block throws
    _ = try parseAge("eighteen")
} catch {
    switch error {                                   // error's type is ParseError
    case .empty: print("Please enter an age")
    case .notANumber(let s): print("“\(s)” is not a number")
    }
}
```

Note `do throws(ParseError)`: it tells the compiler directly that this `do` block throws `ParseError`. In ordinary functions and top-level code you can omit this annotation as long as the only error thrown inside the `do` is `ParseError`; the compiler infers it. **In closures it doesn't**: the braces of `Task { }` are a closure, and so are the braces of `#Playground { }` in an Xcode Playground. If you leave it out there, the `error` in the `catch` falls back to `any Error`:

```swift title="Leaving out throws(ParseError) inside a closure" check=error script expect="has no member 'empty'" hl="13,16"
enum ParseError: Error {
    case empty
    case notANumber(String)
}

func parseAge(_ text: String) throws(ParseError) -> Int {
    guard !text.isEmpty else { throw .empty }
    guard let n = Int(text) else { throw .notANumber(text) }
    return n
}

Task {
    do {                                             // throws(ParseError) is missing
        _ = try parseAge("eighteen")
    } catch {
        switch error {                               // error here is any Error
        case .empty: print("Please enter an age")
        case .notANumber(let s): print("“\(s)” is not a number")
        }
    }
}
```

So the safest style is to always write `do throws(ParseError)`: it compiles inside functions, closures, and Playgrounds alike.

Typed throws is especially handy with generics: the error type can be passed along as a generic parameter, which is more precise than `rethrows`. When you pass a closure that doesn't throw, `E` is inferred as `Never`, and the caller doesn't even need to write `try`:

```swift title="Passing the error type through generics" check=run
extension Sequence {
    func myMap<T, E: Error>(_ transform: (Element) throws(E) -> T) throws(E) -> [T] {
        var result: [T] = []
        for x in self { result.append(try transform(x)) }
        return result
    }
}

let doubled = [1, 2, 3].myMap { $0 * 2 }   // E == Never: no try needed
print(doubled)
```

- `throws` is equivalent to `throws(any Error)`: any error at all, in a [box](#f-some-any). `throws(Never)` is equivalent to not throwing.
- Good for: code inside a module, embedded environments (avoiding the cost of existentials), and cases where the set of errors really is closed.
- Use it carefully in public APIs: the error type becomes part of the API contract, so adding a new kind of error later is a breaking change. The proposal itself also recommends plain `throws` in most cases.

::: quiz
? Which declaration is `func load() throws(Never) -> Data` equivalent to?
- `func load() throws -> Data`
+ `func load() -> Data`
- `func load() rethrows -> Data`
> `Never` has no values, so the function can never throw. It is just an ordinary non-throwing function, and callers don't need `try` either.
:::

## noncopyable-generics
title: "Noncopyable types meet generics: `~Copyable`"
line: 2
se: 0427, 0429, 0432, 0437
level: core
short: ~Copyable generics
tags: noncopyable move-only ~Copyable consuming borrowing ownership deinit Optional
tldr: Swift 5.9 already had noncopyable structs, but they could barely be used with generics, protocols, or `Optional`. Swift 6 lets generic parameters, protocols, and extensions drop the “copyable by default” assumption, and the standard library's `Optional`, `Result`, and pointer types support noncopyable types too.

Every type in Swift is `Copyable` by default: you can copy it freely when you assign or pass it. Writing `~Copyable` means “don't assume I can be copied”. That is ideal for expressing a **unique resource**: a ticket can be punched only once, and a file handle can be closed only once.

```swift title="A ticket that can't be photocopied" check=run
struct Ticket: ~Copyable {
    let id: Int

    consuming func punch() {          // consuming: after the call, this ticket is “used up”
        print("Ticket #\(id) punched")
    }

    deinit { print("Ticket #\(id) recycled") }
}

func ride() {
    let ticket = Ticket(id: 7)
    ticket.punch()
}
ride()
```

```swift title="Want to use it twice? The compiler says no" check=error hl="10,11"
struct Ticket: ~Copyable {
    let id: Int
    consuming func punch() {
        print("Ticket #\(id) punched")
    }
}

func ride() {
    let ticket = Ticket(id: 7)
    ticket.punch()
    ticket.punch()
}
```

The key advance in Swift 6: generics can accept noncopyable types now. The `Wallet` below can hold ordinary values as well as a `Ticket`:

```swift title="A generic container holding a noncopyable value" check=run
struct Ticket: ~Copyable {
    let id: Int
}

struct Wallet<Item: ~Copyable>: ~Copyable {
    var item: Item?

    mutating func take() -> Item? {
        item.take()                      // Optional now supports noncopyable Wrapped types too
    }
}

extension Wallet: Copyable where Item: Copyable {}   // when it holds something copyable, the wallet can be copied too

var wallet = Wallet(item: Ticket(id: 42))
if let t = wallet.take() {
    print("Took out ticket #\(t.id)")
}
print(wallet.item == nil)
```

- `~Copyable` means “**not guaranteed** to be copyable”, not “guaranteed not copyable”: `Wallet<Int>` can still be copied.
- Parameter ownership modifiers: `borrowing` (read-only borrow), `consuming` (take ownership), and `inout` (exclusive mutation). They're explained at the [5.x basics station](#f-borrowing-consuming).
- The same release also supports partial consumption (taking just one field out of a struct) and borrowing `switch` matches on noncopyable enums.
- This is the foundation for `Span`, `InlineArray`, `UniqueArray`, `Continuation`, and other features that follow. Try it hands-on: [Ownership Sandbox](#lab-ownership).

::: quiz
? Which statement about `struct Box<T: ~Copyable>: ~Copyable` is correct?
- `Box<Int>` must also be noncopyable
+ `T` can be a copyable type or a noncopyable type
- `T` must be a noncopyable type
> `~Copyable` removes the “must be copyable by default” constraint; it doesn't require the type to be noncopyable. Combined with `extension Box: Copyable where T: Copyable {}`, `Box<Int>` can be copied.
:::

## pack-iteration
title: "Parameter pack iteration: `for … in repeat each`"
line: 3
se: 0408
level: brief
short: Pack iteration
tags: parameter pack variadic generics repeat each
tldr: Swift 5.9 introduced parameter packs (a variable number of generic parameters), but they could only be “expanded” in expressions. Swift 6.0 lets you iterate over a pack directly with `for-in`.

```swift check=run
func allEqual<each T: Equatable>(_ lhs: repeat each T, to rhs: repeat each T) -> Bool {
    for (left, right) in repeat (each lhs, each rhs) {
        guard left == right else { return false }
    }
    return true
}

print(allEqual(1, "a", 2.5, to: 1, "a", 2.5))   // three arguments, each of a different type
print(allEqual(true, to: false))
```

Note that parameters after a parameter pack must have labels (`to:` here); otherwise the compiler can't tell where one pack ends and the next begins. New to packs? Start at the [5.x basics station](#f-parameter-packs).

## swift-testing
title: "Swift Testing: the next-generation test framework"
line: 6
level: key
short: Swift Testing
tags: Swift Testing @Test #expect #require unit test parameterized XCTest
tldr: An open-source test framework shipped with the Swift 6 toolchain. Mark tests with `@Test` and assert with `#expect`; it supports parameterized tests, parallel execution, and tags natively, and can live alongside XCTest in the same target.

```swift title="@Test, #expect, and parameterized tests" check=ok testing
import Testing

struct Calculator {
    func add(_ a: Int, _ b: Int) -> Int { a + b }
}

@Suite("Calculator")
struct CalculatorTests {
    let calc = Calculator()

    @Test("Adding two positive numbers")
    func addPositive() {
        #expect(calc.add(2, 3) == 5)
    }

    @Test("Addition is commutative", arguments: [(1, 2), (10, -3), (0, 0)])
    func commutative(a: Int, b: Int) {
        #expect(calc.add(a, b) == calc.add(b, a))
    }

    @Test func parse() throws {
        let n = try #require(Int("42"))     // if this fails, the test ends immediately
        #expect(n == 42)
    }
}
```

- `#expect` is a [macro](#f-macros), so it sees the expression you wrote: when it fails, it shows the value of every sub-expression, which is far more informative than `XCTAssertEqual`.
- Each set of arguments in a parameterized test is an independent test case that can be rerun on its own.
- It kept improving release after release: [6.1](#f-testing-61)'s scoping traits, [6.2](#f-testing-62)'s exit tests and attachments, [6.3](#f-testing-63)'s warnings and cancellation, and [6.4](#f-testing-64)'s interoperability with XCTest.
