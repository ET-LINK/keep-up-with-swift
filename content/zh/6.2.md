## default-isolation
title: 默认隔离到主 actor
en: Control default actor isolation inference
line: 1
se: 0466
level: core
short: 默认 MainActor
tags: default isolation MainActor 主线程 主actor 单线程 App 脚本 -default-isolation defaultIsolation Approachable Concurrency
tldr: 一个编译选项，把模块里所有“没写隔离”的代码默认推断为 `@MainActor`。对 App 和脚本来说，大部分代码天然就是单线程的，不用再到处补 `@MainActor`。

Swift 6 模式的一个痛点是：UI 相关的类型大多需要 `@MainActor`，漏写一个，报错就会沿着调用链蔓延。下面的 `ProfilePresenter` 只是忘了标注：

```swift title="没有标注：编译器不知道 Presenter 运行在哪里" check=error
@MainActor
final class ProfileView {
    func show(_ text: String) { print("显示：", text) }
}

final class ProfilePresenter {
    let view = ProfileView()
    func present(name: String) {
        view.show("你好，\(name)")
    }
}
```

```swift title="加上 -default-isolation MainActor：同一段代码直接通过" check=ok flags="-swift-version 6 -default-isolation MainActor"
@MainActor
final class ProfileView {
    func show(_ text: String) { print("显示：", text) }
}

final class ProfilePresenter {
    let view = ProfileView()
    func present(name: String) {
        view.show("你好，\(name)")
    }
}
```

```swift file=Package.swift check=none
.executableTarget(
    name: "MyApp",
    swiftSettings: [
        .defaultIsolation(MainActor.self),
        .enableUpcomingFeature("NonisolatedNonsendingByDefault"),
        .enableUpcomingFeature("InferIsolatedConformances"),
    ]
)
```

- 只影响**没有显式写隔离**的声明；明确写了 `nonisolated`、`@concurrent` 或其他 actor 的代码不受影响。
- 适合 App、命令行工具、脚本这类以主流程为中心的 target；被很多人复用的库（library）通常保持默认的 `nonisolated`。
- Xcode 26 新建的 App 工程默认开启 **Default Actor Isolation = MainActor** 和 **Approachable Concurrency**，后者包含本页的 `NonisolatedNonsendingByDefault` 与 `InferIsolatedConformances`。
- 需要后台工作时，再用 [`@concurrent`](#f-concurrent) 显式标出来。

::: quiz
? 开启 `-default-isolation MainActor` 后，一个显式写了 `nonisolated` 的函数会怎样？
- 也会被改成 `@MainActor`
+ 保持 `nonisolated`，默认值只作用于没有写隔离的声明
- 编译报错，两者冲突
> 默认隔离只是“没写时的默认值”。显式写出的隔离（`nonisolated`、`@concurrent`、`@SomeActor`）永远优先。
:::

## nonsending
title: "`nonisolated(nonsending)`：异步函数默认留在调用者身边"
en: Run nonisolated async functions on the caller's actor by default
line: 1
se: 0461
flag: NonisolatedNonsendingByDefault
level: core
short: nonsending
tags: nonisolated nonsending async 异步 调用者 caller actor 执行器 executor 全局并发 线程池 hop
tldr: 以前 `nonisolated` 的 `async` 函数总是跳到全局并发线程池执行，一调用就“跨了线程”，于是到处是 `Sendable` 报错。现在它默认在**调用者所在的 actor** 上运行，和同步函数的直觉一致。

Swift 5.7 起有一条容易让人困惑的规则：一个不属于任何 actor 的 `async` 函数，被调用时会离开调用者，切换到全局并发执行器（线程池）上运行。所以下面这段再普通不过的代码，在 Swift 6 模式下会报错。`Model` 不是 `Sendable` 的，而调用 `load()` 时它被“带”到了另一个线程：

```swift title="旧规则：nonisolated async 会离开主 actor" check=error
final class Model {
    var items: [String] = []
    func load() async { items.append("新数据") }
}

@MainActor
final class ViewModel {
    let model = Model()
    func refresh() async {
        await model.load()
    }
}
```

注意编译器诊断里的措辞：它已经把旧行为称为 `@concurrent`。开启 upcoming feature 之后，同样的代码直接编译通过，因为 `load()` 现在就在主 actor 上执行，没有任何东西跨越线程：

```swift title="开启 NonisolatedNonsendingByDefault 后" check=ok flags="-swift-version 6 -enable-upcoming-feature NonisolatedNonsendingByDefault"
final class Model {
    var items: [String] = []
    func load() async { items.append("新数据") }
}

@MainActor
final class ViewModel {
    let model = Model()
    func refresh() async {
        await model.load()
    }
}
```

不想整体开启的话，也可以逐个函数显式写出新行为：

```swift title="不开 upcoming feature，逐个函数写 nonisolated(nonsending)" check=ok
final class Model {
    var items: [String] = []
    nonisolated(nonsending) func load() async { items.append("新数据") }
}

@MainActor
final class ViewModel {
    let model = Model()
    func refresh() async {
        await model.load()
    }
}
```

- 同步函数一直是“在调用者的线程上执行”。现在异步函数也一样了，两者的心智模型终于统一。
- 遇到 `await` 挂起时，主线程照样是空闲的，并不会被“卡住”；只是函数的**同步部分**在调用者的 actor 上执行。
- 迁移：`swift package migrate --to-feature NonisolatedNonsendingByDefault` 会给需要保持旧行为的函数自动加上 `@concurrent`。
- 用动画看清两种规则的区别：[并发执行轨迹实验室](#lab-concurrency)。

::: quiz
? 开启 `NonisolatedNonsendingByDefault` 后，在 `@MainActor` 方法里 `await` 一个普通的 `nonisolated async` 函数，它的同步代码在哪里执行？
- 全局并发线程池
+ 主 actor，也就是调用者所在的隔离域
- 一个新创建的线程
> nonsending 的意思是“不把调用交给别的隔离域”，函数继承调用者的隔离。想去后台，就显式写 `@concurrent`。
:::

## concurrent
title: "`@concurrent`：需要并行时，明确说出来"
en: The @concurrent attribute
line: 1
se: 0461
level: core
short: "@concurrent"
tags: concurrent 并行 后台 background 线程池 耗时 解码 主线程
tldr: 想把耗时的工作放到后台线程池？给 `async` 函数加上 `@concurrent`。它总是在全局并发执行器上运行，让主 actor 保持空闲。

新规则一句话：**默认留在原地（nonsending），并行请显式（@concurrent）**。

```swift title="把解码这种重活交给后台" check=ok flags="-swift-version 6 -enable-upcoming-feature NonisolatedNonsendingByDefault"
struct Photo: Sendable {
    let pixels: [UInt8]
}

enum PhotoDecoder {
    @concurrent
    static func decode(_ data: [UInt8]) async -> Photo {
        // 想象这里是一段很耗时的解码
        Photo(pixels: data.map { 255 - $0 })
    }
}

@MainActor
final class PhotoViewModel {
    var photo: Photo?

    func load(_ data: [UInt8]) async {
        photo = await PhotoDecoder.decode(data)    // 解码在后台进行，主线程不被阻塞
    }
}
```

既然 `@concurrent` 函数真的会切换到另一个线程，传给它的参数就必须能安全地跨越隔离边界：

```swift title="@concurrent 跨越了隔离边界，参数必须能安全传递" check=error flags="-swift-version 6 -enable-upcoming-feature NonisolatedNonsendingByDefault"
final class Draft {               // 不是 Sendable
    var text = ""
}

@concurrent
func save(_ draft: Draft) async {
    print(draft.text)
}

@MainActor
final class Editor {
    let draft = Draft()
    func autosave() async {
        await save(draft)
    }
}
```

- `@concurrent` 只能用于 `async` 函数，并且隐含 `nonisolated`。
- 不要把所有函数都标成 `@concurrent`：线程切换本身有成本，而且会带来 `Sendable` 的要求。只给真正耗时的计算加。

## isolated-conformances
title: 隔离一致性：主 actor 类型也能遵守普通协议
en: Global-actor isolated conformances
line: 1
se: 0470
flag: InferIsolatedConformances
level: key
short: 隔离一致性
tags: isolated conformance 协议 一致性 Equatable MainActor protocol 遵循
tldr: 写 `@MainActor Equatable` 表示“这份遵循只在主 actor 上有效”。`@MainActor` 的类型终于可以正常实现 `Equatable`、`Hashable` 这类普通协议，编译器负责保证它不会在别的线程上被调用。

```swift title="以前：主 actor 类型实现 Equatable 会报错" check=error
@MainActor
final class Contact: Equatable {
    var name = ""

    static func == (a: Contact, b: Contact) -> Bool {
        a.name == b.name
    }
}
```

```swift title="Swift 6.2：@MainActor Equatable" check=ok hl="2"
@MainActor
final class Contact: @MainActor Equatable {
    var name = ""

    static func == (a: Contact, b: Contact) -> Bool {
        a.name == b.name
    }
}
```

开启 `InferIsolatedConformances` 后，主 actor 类型的协议遵循会自动推断为隔离的，连 `@MainActor` 都不用写。安全性由编译器保证：如果你试图把这份遵循带到主 actor 之外使用，会直接报错。

```swift title="编译器保证：隔离的遵循不会被带去后台" check=error
protocol Describable {
    func describe() -> String
}

@MainActor
final class Label: @MainActor Describable {
    var text = "你好"
    func describe() -> String { text }
}

@concurrent
func log<T: Describable>(_ value: T) async {
    print(value.describe())
}

@MainActor
func run() async {
    await log(Label())
}
```

## task-immediate
title: "`Task.immediate`：立即在当前上下文开跑"
en: Starting tasks synchronously from caller context
line: 1
se: 0472
level: key
short: Task.immediate
tags: Task immediate 立即 同步 启动 调度 顺序 UI 事件
tldr: 普通的 `Task { }` 只是把任务放进队列，稍后才执行。`Task.immediate { }` 会在当前线程上**立刻**同步执行，直到第一个真正的挂起点。

```swift title="对比执行顺序" check=run
@MainActor
func demo() async {
    print("1. 开始")
    Task {
        print("4. 普通 Task：等当前代码让出主线程后才执行")
    }
    Task.immediate {
        print("2. Task.immediate：立刻同步执行")
    }
    print("3. 回到调用者")
    try? await Task.sleep(for: .milliseconds(50))
}

await demo()
```

适合 UI 事件处理：点击按钮后要立刻更新界面状态（比如显示加载指示），然后再去做异步工作。用普通 `Task` 时，界面可能先渲染一帧旧状态。

## isolated-deinit
title: "`isolated deinit`：在 actor 上执行析构"
en: Isolated synchronous deinit
line: 1
se: 0371
level: brief
short: isolated deinit
tags: deinit 析构 isolated MainActor 清理 cleanup
tldr: `@MainActor` 类的 `deinit` 默认是非隔离的，不能调用主 actor 的方法。写成 `isolated deinit`，析构就会在主 actor 上执行。

```swift title="普通 deinit 不能调用主 actor 方法" check=error
@MainActor
final class SessionController {
    func stopTimers() { print("停止计时器") }

    deinit {
        stopTimers()
    }
}
```

```swift title="isolated deinit" check=ok
@MainActor
final class SessionController {
    func stopTimers() { print("停止计时器") }

    isolated deinit {
        stopTimers()
    }
}
```

如果对象最后一次释放发生在别的线程，运行时会把析构安排到主 actor 上执行，所以析构的时机可能稍晚一些。

## inlinearray
title: "`InlineArray` 与 `[N of T]`：固定长度、不上堆的数组"
en: InlineArray & type sugar
line: 2
se: 0453, 0483
level: core
short: InlineArray
tags: InlineArray 固定大小 fixed-size 数组 栈 stack 堆分配 heap 性能 [N of T]
tldr: "`InlineArray<4, Int>`（简写 `[4 of Int]`）是长度写在类型里的数组：元素直接内联存放在栈上或所属的结构体里，没有堆分配、没有引用计数、没有写时复制。"

`Array` 本身只是一个指针，真正的元素存放在堆上，还附带引用计数和写时复制。对于“长度永远是 4”的数据，这些开销是浪费：

```swift title="和 Array 对比内存布局" check=run
let dynamic: [Int] = [1, 2, 3, 4]
let fixed: [4 of Int] = [1, 2, 3, 4]          // InlineArray<4, Int> 的简写

print(MemoryLayout.size(ofValue: dynamic))     // 只是一个指向堆的指针
print(MemoryLayout.size(ofValue: fixed))       // 四个 Int 就地存放
```

```swift title="基本用法" check=run
var rgb: [3 of UInt8] = [255, 128, 0]
rgb[1] = 200                                   // 可以修改元素
print(rgb.count, rgb[1])

let board = [9 of Character](repeating: "·")  // 用重复值初始化
print(board.count)

for i in rgb.indices {                         // 6.2 中它不是 Sequence，用 indices 遍历
    print(i, rgb[i])
}
```

长度是类型的一部分，所以不能 `append`、不能 `remove`，字面量的元素个数也必须完全一致：

```swift title="元素个数必须和类型一致" check=error
let rgb: [3 of UInt8] = [255, 128]
```

- 适合：小而固定的缓冲区、坐标/颜色/矩阵、嵌入式开发、性能热点。
- 不适合：长度会变化的集合，或者 N 很大的情况（会占用大量栈空间，复制成本也高）。
- 元素可复制时，`InlineArray` 也可复制，而且复制会**真的复制全部元素**，不像 `Array` 那样写时复制。
- Swift 6.4 引入 [`Iterable`](#f-iterable) 后，`InlineArray` 可以直接用 `for-in` 遍历。
- 动手看看不同元素类型的布局：[内存布局实验室](#lab-memory)。

::: quiz
? `MemoryLayout<[5 of Int]>.size` 在 64 位平台上是多少？
- 8，和 `Array` 一样只是一个指针
+ 40，五个 `Int` 全部内联存放
- 48，还要加上一个长度字段
> 长度写在类型里，不需要在运行时存储，所以 `InlineArray` 的大小就是 N × 元素的 stride：5 × 8 = 40。
:::

## integer-generics
title: 整数泛型参数：`<let N: Int>`
en: Integer generic parameters
line: 2
se: 0452
level: key
short: 整数泛型
tags: integer generic 整数泛型 let N value generics 矩阵 matrix 编译期
tldr: 泛型参数不仅可以是类型，还可以是整数：`struct Matrix<let rows: Int, let columns: Int>`。`InlineArray` 的长度参数就是这样实现的。

```swift check=run
struct Matrix<let rows: Int, let columns: Int> {
    var storage: [rows of [columns of Double]]

    init(repeating value: Double) {
        storage = .init(repeating: .init(repeating: value))
    }

    var shape: String { "\(rows)×\(columns)" }    // 在代码里可以像值一样读取
}

let m = Matrix<2, 3>(repeating: 0)
print(m.shape)
print(MemoryLayout<Matrix<2, 3>>.size)    // 6 个 Double，全部内联
```

`Matrix<2, 3>` 和 `Matrix<3, 2>` 是两个不同的类型，所以“形状不匹配”的错误可以在编译期发现。目前整数泛型参数只能是 `Int` 类型的字面量或其他整数泛型参数，还不支持 `N + 1` 这样的计算。

## span
title: "`Span`：安全、零开销地访问连续内存"
en: Span, MutableSpan, RawSpan & friends
line: 2
se: 0447, 0456, 0467, 0485, 0464
level: core
short: Span
tags: Span MutableSpan RawSpan OutputSpan UTF8Span 连续内存 contiguous 指针 pointer 内存安全 lifetime 生命周期
tldr: "`Span<T>` 是一段连续内存的只读视图（`MutableSpan` 可写）。它和 `UnsafeBufferPointer` 一样快，但编译器保证它不会比原始数据活得更久：悬垂指针和释放后使用在编译期就被排除。"

以前，想高效地处理“一段连续的元素”，要么接受 `Array`（可能触发复制），要么用 `withUnsafeBufferPointer` 拿指针（不安全）。`Span` 是第三条路：

```swift title="接受 Span 的函数：Array 和 InlineArray 都能传" check=run
func checksum(_ bytes: Span<UInt8>) -> UInt8 {
    var sum: UInt8 = 0
    for i in bytes.indices {
        sum &+= bytes[i]
    }
    return sum
}

let packet: [UInt8] = [0x12, 0x34, 0x56]
let header: [4 of UInt8] = [1, 2, 3, 4]

print(checksum(packet.span))
print(checksum(header.span))
```

```swift title="MutableSpan：原地修改" check=run
func amplify(_ samples: inout [Float]) {
    var view = samples.mutableSpan       // 独占地借用 samples
    for i in view.indices {
        view[i] *= 2
    }
}

var samples: [Float] = [0.5, -1.2, 3.3]
amplify(&samples)
print(samples)
```

注意上面把 `mutableSpan` 放在函数里使用：`main.swift` 顶层声明的变量其实是全局变量，而全局变量不能持有 `Span` 这类不可逃逸的值。

`Span` 是 `~Escapable` 的：它的生命周期依赖于提供它的数据。试图让它活得比源数据更久，是编译错误，而不是运行时崩溃：

```swift title="Span 不能逃出源数据的作用域" check=error
func leak() -> Int {
    var escaped: Span<UInt8>
    do {
        let data: [UInt8] = [1, 2, 3]
        escaped = data.span
    }
    return escaped.count
}
```

- `Array`、`ContiguousArray`、`ArraySlice`、`InlineArray`、`String.UTF8View` 等都提供 `.span` 属性（SE-0456）。
- `Span` 不能存进全局变量、类的属性或逃逸闭包里；它适合作为函数参数，描述“我只需要临时读一下这些元素”。
- 越界访问依然会在运行时检查，安全性不打折，但没有引用计数和独占性检查的开销。
- 同一家族：`RawSpan`（原始字节）、`MutableSpan`、`OutputSpan`（初始化未初始化的内存）、`UTF8Span`（安全处理 UTF-8）。
- 后续：6.4 的 [`withTemporaryAllocation`](#f-temp-alloc)、[`RawSpan` 安全读取](#f-rawspan-load)，以及与 C++ `std::span` 的双向桥接。

## nonescapable
title: "`~Escapable`：不能逃逸的类型"
en: Nonescapable types
line: 2
se: 0446, 0465
level: brief
short: ~Escapable
tags: Escapable nonescapable 逃逸 lifetime 生命周期 依赖
tldr: "`Span` 背后的语言能力。普通类型默认是 `Escapable` 的，值可以被任意保存和传递；`~Escapable` 类型的值只能在它所依赖的东西还活着的时候使用。"

`~Escapable` 和 `~Copyable` 是一对兄弟：一个去掉“可以复制”的默认能力，一个去掉“可以逃逸”的默认能力。标准库在 6.2 中为它们补齐了基础设施（SE-0465），例如 `Optional` 可以包装不可逃逸的值。

自己定义 `~Escapable` 类型时，需要用生命周期依赖说明“这个值依赖谁”。到 6.4 为止，这部分标注仍然是实验性的（`@_lifetime`），编译器会直接拒绝没有说明依赖关系的写法：

```swift title="没有生命周期标注，编译器无法确认安全" check=error
struct Window: ~Escapable {
    let items: Span<Int>
}
```

日常开发中你多半只会**使用** `Span` 这类现成的不可逃逸类型，而不需要自己定义。

## memory-safety
title: 严格内存安全检查
en: Opt-in strict memory safety checking
line: 2
se: 0458
level: key
short: 内存安全
tags: strict memory safety unsafe 内存安全 指针 pointer 审计 -strict-memory-safety
tldr: 开启 `-strict-memory-safety` 后，所有用到不安全构造（指针、`unsafe` API）的地方都会被标记出来。你可以换成安全的写法，或者用 `unsafe` 表达式明确标注“这里是有意为之”。

```swift title="开启后，不安全的用法会被逐一标记" check=warning flags="-swift-version 6 -strict-memory-safety"
func sum(_ p: UnsafePointer<Int>, count: Int) -> Int {

    for i in 0..<count {
        total += p[i]
    }
    return total
}
```

```swift title="方案一：用 unsafe 明确标注，便于代码审计" check=ok flags="-swift-version 6 -strict-memory-safety"
func sum(_ p: UnsafePointer<Int>, count: Int) -> Int {
    var total = 0
    for i in 0..<count {
        total += unsafe p[i]
    }
    return total
}
```

```swift title="方案二（更好）：换成 Span，警告自然消失" check=ok flags="-swift-version 6 -strict-memory-safety"
func sum(_ values: Span<Int>) -> Int {
    var total = 0
    for i in values.indices {
        total += values[i]
    }
    return total
}
```

这是一个“选择加入”的模式，官方明确表示大多数项目不需要它。它适合安全要求最高的代码：解析不可信输入的组件、加密库、系统服务。`unsafe` 和 `try`、`await` 一样只是标记，不改变运行时行为。

## observations
title: "`Observations`：用异步序列观察 @Observable"
en: Transactional observation of values
line: 4
se: 0475
level: key
short: Observations
tags: Observation Observable Observations async sequence 异步序列 观察 事务 transaction SwiftUI
tldr: "`Observations { … }` 把 `@Observable` 对象的变化变成一个异步序列。同一个事务里的多次修改只产生一次更新，你拿到的始终是一份前后一致的快照。"

```swift title="同时修改两个属性，只收到一次更新" check=run
import Observation

@Observable
final class Cart {
    var count = 0
    var total = 0.0
}

@MainActor
func watch() async {
    let cart = Cart()
    let summaries = Observations { "\(cart.count) 件，共 ¥\(cart.total)" }

    Task {
        for price in [12.5, 30.0] {
            cart.count += 1            // 同一个事务里的两次修改……
            cart.total += price        // ……只会产生一次更新
            try? await Task.sleep(for: .milliseconds(20))
        }
    }

    var received = 0
    for await summary in summaries {
        print(summary)
        received += 1
        if received == 3 { break }
    }
}

await watch()
```

以前在 SwiftUI 之外观察 `@Observable` 只能用 `withObservationTracking`，而且它只通知一次，需要手动重新注册。`Observations` 解决了这个问题。6.4 又补充了更细粒度的控制，见 [高级观察追踪](#f-observation-tracking)。

## nonexhaustive
title: "`@nonexhaustive`：声明“以后可能还会加 case”"
en: Nonexhaustive enums
since: 6.2.3
line: 3
se: 0487
level: brief
short: "@nonexhaustive"
tags: enum 枚举 nonexhaustive 穷尽 unknown default 包 package API 演进
tldr: 普通的 Swift 包里，公开枚举加一个 case 就会让所有使用方的 `switch` 编译失败。标记 `@nonexhaustive` 后，其他模块必须写 `@unknown default`，以后加 case 就不再是破坏性改动。

```swift check=ok
@nonexhaustive
public enum PaymentMethod {
    case card
    case cash
}

// 同一个模块（或同一个包）里，依然可以穷尽 switch，不需要 @unknown default
func label(for method: PaymentMethod) -> String {
    switch method {
    case .card: "刷卡"
    case .cash: "现金"
    }
}
```

以前只有开启了库演进（library evolution）的二进制框架才有这种“非冻结枚举”。这个特性在 Swift 6.2.3 中加入。
