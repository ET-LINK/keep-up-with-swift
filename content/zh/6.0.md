## swift6-mode
title: Swift 6 语言模式：数据竞争变成编译错误
en: Swift 6 language mode & complete concurrency checking
line: 1
se: 0337, 0412, 0414
level: core
short: Swift 6 模式
tags: 数据竞争 data race Sendable strict concurrency 语言模式 language mode swiftLanguageModes 迁移
tldr: 在 Swift 6 语言模式下，编译器会对整个模块做完整的并发检查：任何**可能**发生的数据竞争都是编译错误，而不是上线后才偶尔出现的崩溃。

Swift 5.5 引入了 `async`/`await` 和 actor，但并发检查一直是“建议性”的：一段有数据竞争的代码，可以安安静静地通过编译。Swift 6 编译器新增了 **Swift 6 语言模式**（language mode），在这个模式下，`Sendable` 检查和 actor 隔离检查全部变成错误。

先看一段典型的问题代码。一个普通的类被两个并发执行的地方同时修改：

```swift title="Swift 5 模式：顺利编译，但这里藏着数据竞争" check=ok flags="-swift-version 5"
final class Counter {
    var value = 0
}

func race() {
    let counter = Counter()
    Task.detached {
        counter.value += 1      // 后台线程写入
    }
    counter.value += 1          // 同时在当前线程写入
}
```

同一段代码，切到 Swift 6 模式，编译器会精确地指出冲突的两处访问：

```swift title="同一段代码，Swift 6 模式" check=error flags="-swift-version 6" hl="7,10"
final class Counter {
    var value = 0
}

func race() {
    let counter = Counter()
    Task.detached {
        counter.value += 1      // 后台线程写入
    }
    counter.value += 1          // 同时在当前线程写入
}
```

全局可变状态是另一类常见问题：任何线程都可以随时读写一个 `static var`。Swift 6 模式要求你说清楚它由谁来保护：

```swift title="全局可变状态同样会被拦下" check=error
struct Settings {
    static var current = Settings()
    var theme = "light"
}
```

```swift title="三种修法，任选其一" check=ok
struct Settings {
    static let standard = Settings()                    // ① 改成不可变的 let
    @MainActor static var current = Settings()          // ② 交给主 actor 保护
    nonisolated(unsafe) static var legacy = Settings()  // ③ 自己保证同步（慎用）
    var theme = "light"
}
```

### 如何开启、如何迁移

语言模式和编译器版本是两回事：Swift 6.0 到 6.4 的编译器都同时支持 Swift 5 和 Swift 6 两种模式，你可以按 target 逐个迁移。

```swift file=Package.swift check=none
// swift-tools-version: 6.0
import PackageDescription

let package = Package(
    name: "MyApp",
    targets: [
        .target(name: "Core"),                           // tools-version 6.0：默认 Swift 6 模式
        .target(
            name: "Legacy",
            swiftSettings: [.swiftLanguageMode(.v5)]     // 这个 target 暂时留在 Swift 5 模式
        ),
    ]
)
```

- 迁移前，可以先在 Swift 5 模式下加上 `-strict-concurrency=complete`，把同样的问题以**警告**形式提前看到，逐个修掉再切换。
- 在 Xcode 中对应 Build Settings 里的 **Swift Language Version**。
- 不要一上来就到处加 `@unchecked Sendable` 或 `nonisolated(unsafe)`：它们只是让编译器闭嘴，问题还在。
- 后面几个版本的大量工作（尤其是 [6.2 的“平易近人的并发”](#v62)）都是为了让 Swift 6 模式更好用、报错更少。

::: quiz
? 把一个 Swift 5 项目直接换到 Swift 6.0 编译器（Xcode 16）上编译，会发生什么？
- 立刻出现大量数据竞争错误，必须全部修完才能编译
+ 照常编译：项目的语言模式仍是 Swift 5，要主动切换到 Swift 6 模式才会启用完整检查
- 编译器不再支持 Swift 5 的语法
> 新编译器默认保持项目原来的语言模式。Swift 6 模式需要主动开启，而且可以按 target 分别开启。
:::

## region-sending
title: 区域隔离与 `sending`：编译器看懂了“交接”
en: Region-based isolation & sending
line: 1
se: 0414, 0430
level: core
short: sending
tags: region isolation 区域 sending transferring Sendable 非Sendable 交接
tldr: 非 `Sendable` 的值也可以安全地交给另一个任务，只要编译器能证明你之后不会再碰它。`sending` 关键字把这种“交接”写进函数签名。

早期的严格并发检查规则很死板：只要一个类型不是 `Sendable`，它的值就不能跨越隔离边界，哪怕你只是新建了一个对象，然后把它整个交给后台任务。

SE-0414 引入了**区域隔离**（region-based isolation）。编译器会追踪每个值属于哪个“区域”：如果一个区域被整体交出去，并且之后再也不用，那么这次交接就是安全的。

```swift title="新建的对象交给后台任务，之后不再碰它：没问题" check=ok
final class Report {
    var lines: [String] = []
}

func generate() {
    let report = Report()
    report.lines.append("标题")
    Task.detached {
        report.lines.append("正文")    // report 所在的整个区域被交给了这个任务
    }
    // 之后不再访问 report → 编译通过
}
```

```swift title="交出去之后又用了它：编译器精确指出冲突" check=error hl="11"
final class Report {
    var lines: [String] = []
}

func generate() {
    let report = Report()
    report.lines.append("标题")
    Task.detached {
        report.lines.append("正文")
    }
    report.lines.append("结尾")        // 和后台任务同时访问
}
```

### 用 `sending` 把交接写进 API

`Task.detached` 能接收上面的闭包，是因为它的参数被标记为 `sending`：调用方承诺把这个值交出去、之后不再使用。你自己的函数也可以这样声明：

```swift title="普通参数属于调用方的区域，不能随手交给别的任务" check=error
final class Photo {
    var pixels: [UInt8] = []
}

func process(_ photo: Photo) {
    Task.detached {
        photo.pixels.append(0)
    }
}
```

```swift title="标记为 sending：调用方负责交出所有权" check=ok
final class Photo {
    var pixels: [UInt8] = []
}

func process(_ photo: sending Photo) {
    Task.detached {
        photo.pixels.append(0)        // ✅ photo 已经和调用方断开了
    }
}

func makePhoto() -> sending Photo {   // 返回值也可以是 sending：一个与任何人都不共享的新值
    Photo()
}

func upload() {
    process(makePhoto())
}
```

- 区域隔离不需要你写任何代码，升级编译器就生效；很多以前要靠 `@unchecked Sendable` 绕过的地方，现在可以直接编译。
- `sending` 参数：调用方交出值，被调用方可以把它再交给别的隔离域。`sending` 返回值：返回一个“干净的”新值。
- 提案早期叫 `transferring`，最终定名为 `sending`。

## synchronization
title: "`Mutex` 与 `Atomic`：标准库自带同步原语"
en: Synchronization module
line: 1
se: 0410, 0433
level: key
short: Mutex·Atomic
tags: Mutex Atomic 锁 lock Synchronization 原子 线程安全 Sendable
tldr: 新的 `Synchronization` 模块提供 `Mutex` 和 `Atomic`。用它们保护内部状态的类型，可以安全地声明为 `Sendable`，不再需要 `@unchecked`。

以前要写一个线程安全的类，通常要用 `NSLock`、`os_unfair_lock` 或者 `DispatchQueue`，再给类型加上 `@unchecked Sendable`，告诉编译器“相信我”。现在标准库直接提供了锁和原子类型，编译器能理解它们的安全性：

```swift title="用 Mutex 保护缓存，类型可以诚实地声明 Sendable" check=run
import Synchronization

final class ImageCache: Sendable {
    private let storage = Mutex<[String: Int]>([:])

    func insert(_ size: Int, for key: String) {
        storage.withLock { $0[key] = size }
    }

    func size(for key: String) -> Int? {
        storage.withLock { $0[key] }
    }
}

let cache = ImageCache()
cache.insert(1024, for: "avatar.png")
print(cache.size(for: "avatar.png") ?? 0)
```

```swift title="Atomic：无锁的计数器" check=run
import Synchronization

final class Stats: Sendable {
    let visits = Atomic<Int>(0)
}

let stats = Stats()
await withTaskGroup { group in
    for _ in 0..<100 {
        group.addTask { stats.visits.add(1, ordering: .relaxed) }
    }
}
print(stats.visits.load(ordering: .relaxed))
```

- `Mutex` 和 `Atomic` 都是 `~Copyable`（不可复制）类型：存成 `let` 属性，通过借用访问，不会被意外复制出第二把锁。
- 需要 macOS 15、iOS 18 等系统版本对应的运行时。
- 多数情况下仍然优先考虑 actor；在同步代码、性能敏感的路径，或者不想引入 `await` 的地方，`Mutex` 更合适。

## isolation-inherit
title: "`#isolation`：让函数继承调用者的隔离"
en: Inheritance of actor isolation
line: 1
se: 0420, 0431
level: brief
short: "#isolation"
tags: isolation isolated 参数 继承 actor isolated(any)
tldr: 给异步函数加一个 `isolated (any Actor)? = #isolation` 参数，它就会在调用者所在的 actor 上运行，可以安全地操作调用者的非 `Sendable` 状态。

```swift title="一个“跟着调用者走”的计时工具" check=ok
func measure<T>(
    _ label: String,
    isolation: isolated (any Actor)? = #isolation,
    _ body: () async throws -> T
) async rethrows -> T {
    let start = ContinuousClock.now
    defer { print(label, ContinuousClock.now - start) }
    return try await body()
}

@MainActor
final class Feed {
    var items: [String] = []

    func reload() async {
        await measure("reload") {
            items = ["新闻 A", "新闻 B"]   // measure 和闭包都运行在主 actor 上
        }
    }
}
```

这个写法有点啰嗦：`(any Actor)?` 是[能装任何 actor 的盒子](#f-some-any)，调用者不属于任何 actor 时就是 `nil`。到了 Swift 6.2，[`nonisolated(nonsending)`](#f-nonsending) 让“异步函数继承调用者的隔离”变成了默认行为，大多数情况下不再需要手写这个参数。同一版本还加入了 `@isolated(any)` 函数类型，让持有闭包的一方可以查询它的隔离（`Task` 的初始化方法就用到了它）。

## typed-throws
title: 类型化抛出 `throws(E)`
en: Typed throws
line: 3
se: 0413
level: core
short: 类型化抛出
tags: typed throws 错误处理 error handling catch Never rethrows
tldr: 函数可以声明自己只会抛出某一种错误：`throws(ParseError)`。调用方 `catch` 到的直接就是 `ParseError`，可以穷尽地 `switch`，不用再 `as?` 猜类型。

```swift title="以前：catch 里只有 any Error" check=run
enum ParseError: Error {
    case empty
    case notANumber(String)
}

func parseAge(_ text: String) throws -> Int {
    guard !text.isEmpty else { throw ParseError.empty }
    guard let n = Int(text) else { throw ParseError.notANumber(text) }
    return n
}

do {
    _ = try parseAge("十八")
} catch let error as ParseError {     // 需要自己转换类型
    print("解析失败：", error)
} catch {
    print("不会发生，但编译器要求兜底：", error)
}
```

```swift title="现在：throws(ParseError)" check=run hl="6,12-13,15-18"
enum ParseError: Error {
    case empty
    case notANumber(String)
}

func parseAge(_ text: String) throws(ParseError) -> Int {
    guard !text.isEmpty else { throw .empty }        // 可以省略类型名
    guard let n = Int(text) else { throw .notANumber(text) }
    return n
}

do throws(ParseError) {                              // 写明这个 do 块抛出的错误类型
    _ = try parseAge("十八")
} catch {
    switch error {                                   // error 的类型就是 ParseError
    case .empty: print("请输入年龄")
    case .notANumber(let s): print("“\(s)”不是数字")
    }
}
```

注意 `do throws(ParseError)`：它直接告诉编译器，这个 `do` 块抛出的错误类型是 `ParseError`。在普通函数和顶层代码里，只要 `do` 里抛出的只有 `ParseError` 一种错误，这个标注可以省略，编译器会自己推断。但**在闭包里不会**：`Task { }` 的花括号是闭包，Xcode Playground 里 `#Playground { }` 的花括号也是。漏写时，`catch` 里的 `error` 就退回成 `any Error`：

```swift title="闭包里漏写 throws(ParseError)" check=error script expect="has no member 'empty'" hl="13,16"
enum ParseError: Error {
    case empty
    case notANumber(String)
}

func parseAge(_ text: String) throws(ParseError) -> Int {
    guard !text.isEmpty else { throw .empty }
    guard let n = Int(text) else { throw .notANumber(text) }
    return n
}

Task {
    do {                                             // 少了 throws(ParseError)
        _ = try parseAge("十八")
    } catch {
        switch error {                               // 这里的 error 是 any Error
        case .empty: print("请输入年龄")
        case .notANumber(let s): print("“\(s)”不是数字")
        }
    }
}
```

所以最稳妥的写法是总带上 `do throws(ParseError)`：放在函数里、闭包里、Playground 里都能编译。

类型化抛出在泛型里尤其好用：错误类型可以作为泛型参数传递，比 `rethrows` 更精确。传入不抛错的闭包时，`E` 被推断为 `Never`，调用方连 `try` 都不用写：

```swift title="泛型里传递错误类型" check=run
extension Sequence {
    func myMap<T, E: Error>(_ transform: (Element) throws(E) -> T) throws(E) -> [T] {
        var result: [T] = []
        for x in self { result.append(try transform(x)) }
        return result
    }
}

let doubled = [1, 2, 3].myMap { $0 * 2 }   // E == Never：不需要 try
print(doubled)
```

- `throws` 等价于 `throws(any Error)`，也就是装在[盒子](#f-some-any)里的任意错误；`throws(Never)` 等价于不抛出。
- 适合：模块内部的代码、嵌入式环境（避免存在类型的开销）、错误种类确实是封闭集合的场景。
- 公共 API 要慎用：错误类型会成为 API 契约的一部分，以后想加一种新错误就是破坏性改动。提案本身也建议多数情况继续使用普通的 `throws`。

::: quiz
? `func load() throws(Never) -> Data` 等价于下面哪个声明？
- `func load() throws -> Data`
+ `func load() -> Data`
- `func load() rethrows -> Data`
> `Never` 没有任何值，函数永远不可能抛出错误，所以它就是一个普通的不抛错函数，调用时也不需要 `try`。
:::

## noncopyable-generics
title: 不可复制类型走进泛型：`~Copyable`
en: Noncopyable generics
line: 2
se: 0427, 0429, 0432, 0437
level: core
short: ~Copyable 泛型
tags: noncopyable move-only ~Copyable consuming borrowing 所有权 ownership deinit Optional
tldr: Swift 5.9 就有了不可复制的结构体，但它们几乎不能和泛型、协议、`Optional` 一起用。Swift 6 让泛型参数、协议和扩展都可以去掉“默认可复制”的假设，标准库的 `Optional`、`Result`、指针类型也都支持了不可复制类型。

Swift 里每个类型默认都是 `Copyable` 的：赋值、传参时可以随意复制。写上 `~Copyable` 的意思是“不要假设我可以被复制”。这非常适合表达**唯一的资源**：一张车票只能检一次，一个文件句柄只能关闭一次。

```swift title="一张不能复印的车票" check=run
struct Ticket: ~Copyable {
    let id: Int

    consuming func punch() {          // consuming：调用之后，这张票就被“用掉”了
        print("第 \(id) 号票已检票")
    }

    deinit { print("第 \(id) 号票被回收") }
}

func ride() {
    let ticket = Ticket(id: 7)
    ticket.punch()
}
ride()
```

```swift title="想用两次？编译器不答应" check=error hl="10,11"
struct Ticket: ~Copyable {
    let id: Int
    consuming func punch() {
        print("第 \(id) 号票已检票")
    }
}

func ride() {
    let ticket = Ticket(id: 7)
    ticket.punch()
    ticket.punch()
}
```

Swift 6 的关键进步是：泛型也能接纳不可复制的类型了。下面的 `Wallet` 既能装普通值，也能装 `Ticket`：

```swift title="泛型容器装下不可复制的值" check=run
struct Ticket: ~Copyable {
    let id: Int
}

struct Wallet<Item: ~Copyable>: ~Copyable {
    var item: Item?

    mutating func take() -> Item? {
        item.take()                      // Optional 现在也支持不可复制的 Wrapped
    }
}

extension Wallet: Copyable where Item: Copyable {}   // 装可复制的东西时，钱包也可以复制

var wallet = Wallet(item: Ticket(id: 42))
if let t = wallet.take() {
    print("取出了 \(t.id) 号票")
}
print(wallet.item == nil)
```

- `~Copyable` 的含义是“**不保证**可复制”，而不是“保证不可复制”：`Wallet<Int>` 依然可以复制。
- 参数的所有权修饰：`borrowing`（只读借用）、`consuming`（拿走所有权）、`inout`（独占地修改），详见 [5.x 的基础站](#f-borrowing-consuming)。
- 同一版本还支持了部分消耗（只拿走结构体里的某个字段）和对不可复制枚举的 `switch` 借用匹配。
- 这是后面 `Span`、`InlineArray`、`UniqueArray`、`Continuation` 等特性的地基。动手试试：[所有权沙盒](#lab-ownership)。

::: quiz
? 下面关于 `struct Box<T: ~Copyable>: ~Copyable` 的说法，哪一个是对的？
- `Box<Int>` 也一定是不可复制的
+ `T` 可以是可复制的类型，也可以是不可复制的类型
- `T` 必须是不可复制的类型
> `~Copyable` 去掉的是“默认要求可复制”这个约束，并不要求类型一定不可复制。再配合 `extension Box: Copyable where T: Copyable {}`，`Box<Int>` 就能复制。
:::

level: brief
short: 参数包遍历
tags: parameter pack variadic generics repeat each 可变参数 泛型
tldr: Swift 5.9 引入了参数包（可变数量的泛型参数），但只能在表达式里“展开”。Swift 6.0 允许直接用 `for-in` 遍历一个参数包。

```swift check=run
func allEqual<each T: Equatable>(_ lhs: repeat each T, to rhs: repeat each T) -> Bool {
    for (left, right) in repeat (each lhs, each rhs) {
        guard left == right else { return false }
    }
    return true
}

print(allEqual(1, "a", 2.5, to: 1, "a", 2.5))   // 三个参数，类型各不相同
print(allEqual(true, to: false))
```

注意参数包之后的参数必须带标签（这里是 `to:`），否则编译器无法区分两个包的边界。还不熟悉参数包？先看 [5.x 的基础站](#f-parameter-packs)。

## swift-testing
title: Swift Testing：新一代测试框架
en: Swift Testing
line: 6
level: key
short: Swift Testing
tags: Swift Testing @Test #expect #require 单元测试 unit test 参数化 parameterized XCTest
tldr: 随 Swift 6 工具链发布的开源测试框架：用 `@Test` 标记测试、用 `#expect` 断言，原生支持参数化测试、并行执行和标签，可以和 XCTest 在同一个 target 里共存。

```swift title="@Test、#expect 与参数化测试" check=ok testing
import Testing

struct Calculator {
    func add(_ a: Int, _ b: Int) -> Int { a + b }
}

@Suite("计算器")
struct CalculatorTests {
    let calc = Calculator()

    @Test("两个正数相加")
    func addPositive() {
        #expect(calc.add(2, 3) == 5)
    }

    @Test("加法满足交换律", arguments: [(1, 2), (10, -3), (0, 0)])
    func commutative(a: Int, b: Int) {
        #expect(calc.add(a, b) == calc.add(b, a))
    }

    @Test func parse() throws {
        let n = try #require(Int("42"))     // 失败就立即结束这个测试
        #expect(n == 42)
    }
}
```

- `#expect` 是一个[宏](#f-macros)，看得到你写的表达式本身：失败时，会展示表达式里每个子表达式的值，比 `XCTAssertEqual` 直观得多。
- 参数化测试的每组参数都是独立的测试用例，可以单独重跑。
- 后续版本一路增强：[6.1](#f-testing-61) 的作用域特性、[6.2](#f-testing-62) 的退出测试与附件、[6.3](#f-testing-63) 的警告和取消、[6.4](#f-testing-64) 与 XCTest 互通。

tldr: 给类型加上 `@DebugDescription` 宏，LLDB 在变量窗口和崩溃报告里就会直接显示你定义的摘要，不需要运行代码。

```swift check=ok
@DebugDescription
struct Order: CustomDebugStringConvertible {
    var id: Int
    var total: Double

    var debugDescription: String { "订单 #\(id)：¥\(total)" }
}
```

这个[宏](#f-macros)会把 `debugDescription` 编译成 LLDB 的摘要格式并嵌入二进制，所以它只能使用简单的字符串插值（存储属性），不能调用任意函数。
