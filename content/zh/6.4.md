## async-defer
title: "`defer` 里可以 `await` 了"
en: Support async calls in defer bodies
line: 1
se: 0493
level: core
short: async defer
tags: defer async await 清理 cleanup 资源 关闭 close 异步
tldr: 在异步函数里，`defer` 块现在可以包含 `await`。离开作用域时，异步清理会被完整地等待执行完，再真正返回。

以前想做异步清理，只能在每个 `return` 和 `catch` 前面手动写一遍，或者在 `defer` 里开一个 `Task { }`，后者既不保证执行顺序，也不保证在函数返回前完成。

```swift title="异步清理也能被保证执行" check=run
struct Connection {
    func send(_ message: String) async throws { print("发送：", message) }
    func close() async { print("连接已关闭") }
}

func sync(over connection: Connection) async throws {
    defer { await connection.close() }
    try await connection.send("你好")
    try await connection.send("再见")
}

try await sync(over: Connection())
```

`await` 只能出现在本身就是 `async` 的上下文里，同步函数的 `defer` 依然不能挂起：

```swift title="同步函数里不行" check=error
func cleanup() async {}

func work() {
    defer { await cleanup() }
    print("工作中")
}
```

## cancel-shield
title: 取消屏蔽：`withTaskCancellationShield`
en: Task cancellation shields
line: 1
se: 0504
level: core
short: 取消屏蔽
tags: cancellation 取消 shield 屏蔽 Task isCancelled 清理 cleanup defer
tldr: 任务被取消后，清理代码里的网络请求、文件写入往往会因为“看到了取消”而提前放弃。把它们包进 `withTaskCancellationShield { }`，里面的代码就会像任务没被取消一样运行完。

```swift check=run
func flushLogs() async {
    print("  上传日志时看到的取消状态：", Task.isCancelled)
}

let task = Task {
    try? await Task.sleep(for: .seconds(10))      // 被取消后会立刻醒来
    print("任务被取消了吗？", Task.isCancelled)
    await withTaskCancellationShield {
        await flushLogs()                           // 屏蔽区里“看不到”取消
    }
}
task.cancel()
await task.value
```

它和 [`async defer`](#f-async-defer) 是绝配，官方发布说明里的例子就是这样：

```swift title="无论怎样退出，都要把指标上报完" check=ok
func uploadMetrics(for path: String) async {}
func parse(_ path: String) async throws {}

func processFile(at path: String) async throws {
    defer {
        await withTaskCancellationShield {
            await uploadMetrics(for: path)     // 即使任务已被取消，也会完整执行
        }
    }
    try await parse(path)
}
```

- 屏蔽**不会**阻止任务被取消，只是让屏蔽区内的代码观察不到取消；离开屏蔽区后，`Task.isCancelled` 照样是 `true`。
- 在屏蔽区里创建的子任务（`async let`、任务组）也不会被自动取消。
- 只把真正必须完成的清理工作放进去，不要用它来“忽略取消”。

## tilde-sendable

## continuation
title: 新的 `Continuation`：不可能恢复两次的续体
en: Continuation, safe and performant async continuations
line: 1
se: 0528
level: key
short: Continuation
tags: Continuation withContinuation CheckedContinuation UnsafeContinuation 回调 callback 桥接 resume ~Copyable
tldr: "`withContinuation` 提供的 `Continuation` 是 `~Copyable` 的，`resume` 会消耗它。“恢复两次”在编译期就会报错，而且没有 `CheckedContinuation` 的运行时开销。"

```swift title="把一个等待者存起来，稍后再恢复" check=run
actor Doorbell {
    private var waiter: Continuation<String, Never>?

    func wait() async -> String {
        await withContinuation(of: String.self) { continuation in
            waiter = consume continuation           // 移动进存储属性
        }
    }

    func ring(_ visitor: String) {
        waiter.take()?.resume(returning: visitor)   // take() 取出并置空，最多恢复一次
    }
}

let bell = Doorbell()
async let visitor = bell.wait()
try? await Task.sleep(for: .milliseconds(50))
await bell.ring("快递员")
print(await visitor)
```

```swift title="恢复两次？编译期错误" check=error
func twice() async -> Int {
    await withContinuation(of: Int.self) { continuation in
        continuation.resume(returning: 1)
        continuation.resume(returning: 2)
    }
}
```

不过，典型的“回调式 API”往往是逃逸闭包，而编译器无法保证逃逸闭包恰好执行一次，所以不可复制的续体不能在里面被消耗：

```swift title="逃逸闭包里不能消耗它" check=error
func legacyFetch(_ done: @escaping @Sendable (String) -> Void) { done("数据") }

func fetch() async -> String {
    await withContinuation(of: String.self) { continuation in
        legacyFetch { value in continuation.resume(returning: value) }
    }
}
```

这种场景可以把它转换成 `CheckedContinuation(continuation)`，由运行时检查来兜底。新类型如果在没被恢复的情况下就被销毁，会直接触发 `fatalError`，而不是让等待它的任务永远挂起。

## optional-some
title: "`some P?`：可选的不透明类型、存在类型不用加括号"
en: Improved syntax for optionals of opaque and existential types
line: 3
se: 0521
level: key
short: some P?
tags: some any opaque existential 不透明 存在类型 optional 可选 括号
tldr: 以前必须写 `(some Shape)?` 和 `(any Shape)?`，现在 `some Shape?`、`any Shape?` 就是同样的意思。

```swift check=run
protocol Shape {
    var area: Double { get }
}

struct Square: Shape {
    var side: Double
    var area: Double { side * side }
}

func largest(_ sides: [Double]) -> some Shape? {     // 以前：(some Shape)?
    sides.max().map { Square(side: $0) }
}

let shape: any Shape? = largest([2, 5, 3])           // 以前：(any Shape)?
print(shape?.area ?? 0)
```

组合类型仍然需要括号来消除歧义：写 `any (P & Q)?`，而 `any P & Q?` 依然是错误。

## borrow-mutate
title: "`borrow` / `mutate` 访问器：不复制地读写属性"
en: Borrow and mutate accessors
line: 2
se: 0507
level: core
short: borrow·mutate
tags: borrow mutate accessor 访问器 get set _read _modify 复制 copy ~Copyable 性能
tldr: 计算属性的 `get` 总是返回一份**副本**：对大值很浪费，对不可复制的值根本做不到。`borrow` 访问器直接借出存储，`mutate` 访问器直接交出可修改的引用。

```swift check=run
struct Sensor: ~Copyable {
    var readings: [4 of Double] = [0, 0, 0, 0]
}

struct Station: ~Copyable {
    private var _sensor = Sensor()

    var sensor: Sensor {
        borrow { return _sensor }        // 只读地借出，不复制
        mutate { return &_sensor }       // 交出可修改的引用，原地修改
    }
}

var station = Station()
station.sensor.readings[2] = 36.6       // 通过 mutate
print(station.sensor.readings[2])       // 通过 borrow
```

- 以前标准库内部用的是带下划线的 `_read` / `_modify` 协程访问器；`borrow` / `mutate` 不需要协程，开销更低。
- 需要在访问前后执行代码的场景（比如加锁），可以用另一个提案中的 `yielding borrow` / `yielding mutate`。
- 6.4 的发布说明特别提到：属性可以借此直接暴露 `Span` 或 `InlineArray` 供读取和修改。

## noncopyable-protocols
title: 不可复制类型也能 `Equatable`、`Comparable`、`Hashable`
en: Support ~Copyable, ~Escapable in simple standard library protocols
line: 2
se: 0499
level: brief
short: ~Copyable 协议
tags: Equatable Hashable Comparable ~Copyable ~Escapable 协议 protocol borrowing
tldr: 标准库把 `Equatable`、`Comparable`、`Hashable` 的要求改成了 `borrowing` 参数，不可复制、不可逃逸的类型也能遵循它们了。

```swift check=run
struct AccessKey: ~Copyable, Hashable {
    let raw: UInt64

    static func == (a: borrowing AccessKey, b: borrowing AccessKey) -> Bool {
        a.raw == b.raw
    }

    func hash(into hasher: inout Hasher) {
        hasher.combine(raw)
    }
}

let k1 = AccessKey(raw: 42)
let k2 = AccessKey(raw: 42)
print(k1 == k2, k1 != AccessKey(raw: 7))
```

注意：`Set` 和 `Dictionary` 仍然要求元素可复制，所以不可复制的类型目前还不能放进去。

## unique-box-array
title: "`UniqueBox` 与 `UniqueArray`：只有一个主人的堆内存"
en: UniqueBox & UniqueArray
line: 2
se: 0517, 0527
level: core
short: UniqueArray
tags: UniqueArray UniqueBox Box 堆 heap 所有权 ~Copyable 写时复制 COW vector Vec unique_ptr
tldr: "`UniqueArray` 是没有写时复制、没有引用计数的动态数组，元素可以是不可复制的；`UniqueBox` 把一个值放到堆上并独占它。两者都是 `~Copyable`，赋值就是**移动**。"

```swift check=run
struct Frame: ~Copyable {
    let index: Int
    deinit { print("释放第 \(index) 帧") }
}

func render() {
    var frames = UniqueArray<Frame>()         // 元素可以是不可复制的
    frames.append(Frame(index: 1))
    frames.append(Frame(index: 2))
    print("共 \(frames.count) 帧")

    var buffer = UniqueBox<[1024 of UInt8]>(.init(repeating: 0))   // 1 KB 放到堆上
    buffer.value[0] = 0xFF
    print("首字节：", buffer.value[0])
}                                              // 离开作用域：自动释放

render()
```

- `UniqueArray` 类似 C++ 的 `std::vector` 和 Rust 的 `Vec`：自动扩容，但永远只有一个所有者，`let b = a` 会让 `a` 失效。
- `UniqueBox` 类似 `unique_ptr` / `Box<T>`：适合很大的值（避免栈上复制），或递归的数据结构。
- 写普通业务代码时，`Array` 依然是首选；这两个类型面向性能敏感、需要确定性的场景。

## ref
title: "`Ref` 与 `MutableRef`：一等公民的引用"
en: Ref and MutableRef
line: 2
se: 0519
level: key
short: Ref
tags: Ref MutableRef 引用 reference borrow 借用 inout ~Escapable lifetime
tldr: "`borrowing` 和 `inout` 只能出现在参数上。`Ref` / `MutableRef` 把“借用”变成了一个可以存进局部变量、传来传去的值，生命周期由编译器检查。"

```swift check=run
struct Settings: ~Copyable {
    var volume = 50
}

func demo() {
    var settings = Settings()

    do {
        var editor = MutableRef(&settings)   // 独占地借用 settings
        editor.value.volume += 10
        // editor 存活期间，不能再直接访问 settings
    }
    print(settings.volume)

    let viewer = Ref(settings)               // 共享借用：只读
    print(viewer.value.volume)
}

demo()
```

两者都是 `~Escapable` 的，不能比被引用的值活得更久。可以把它们理解为：安全版本的指针，“悬垂”和“别名冲突”都在编译期被排除。

## iterable
title: "`Iterable`：借用式遍历"
en: Iterable
line: 2
se: 0516
level: key
short: Iterable
tags: Iterable Sequence for-in 遍历 borrowing iterator ~Copyable InlineArray UniqueArray Span
tldr: "`Sequence` 的迭代器要把每个元素**复制**出来，不可复制的元素因此没法遍历。新的 `Iterable` 协议按 `Span` 一段一段地借出元素，`for-in` 不复制也不消耗。"

```swift check=run
struct Ticket: ~Copyable {
    let seat: String
}

var tickets = UniqueArray<Ticket>()
tickets.append(Ticket(seat: "3A"))
tickets.append(Ticket(seat: "7C"))

for ticket in tickets {          // 逐个借用：不复制，也不消耗
    print("座位", ticket.seat)
}

let rgb: [3 of UInt8] = [255, 128, 0]
for channel in rgb {             // 6.2 里做不到，现在 InlineArray 可以直接 for-in
    print(channel)
}
```

`Iterable` 的迭代器通过 `nextSpan()` 一次交出一段连续的元素，对于底层是连续内存的类型（数组、`InlineArray`），这也更容易被优化。它还支持通过 `Failure` 类型实现类型化抛出的遍历。

## temp-alloc

## rawspan-load
title: "`RawSpan`：安全地按类型读取字节"
en: Safe loading API for RawSpan
line: 2
se: 0525
level: brief
short: 读取字节
tags: RawSpan bytes 字节 load 解析 parsing 二进制 binary ConvertibleFromBytes
tldr: 从一段原始字节里读出 `UInt16`、`UInt32`，不再需要不安全的指针 API。只有“任意比特都合法”的类型（例如整数）才允许这样读取。

```swift check=run
// 一个简单的二进制头部：版本(UInt16) 标志(UInt16) 长度(UInt32)，小端序
func parseHeader(_ packet: [UInt8]) -> (UInt16, UInt16, UInt32) {
    let bytes = packet.span.bytes                           // RawSpan
    return (
        bytes.load(fromByteOffset: 0, as: UInt16.self),
        bytes.load(fromByteOffset: 2, as: UInt16.self),
        bytes.load(fromByteOffset: 4, as: UInt32.self),
    )
}

print(parseHeader([0x01, 0x00, 0x03, 0x00, 0x2A, 0x00, 0x00, 0x00]))
```

背后是两个新的标记协议：`ConvertibleFromBytes`（任何比特组合都是合法值，比如整数）和 `ConvertibleToBytes`（没有填充字节，可以安全地看作字节）。`Bool`、指针、`Range` 这样有“非法比特组合”或语义约束的类型都不会遵循它们。
